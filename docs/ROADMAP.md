# Дорожная карта

Что строим и скоуп — [v1.0-scope.md](v1.0-scope.md) (исходное ТЗ —
[archive/p2p-messenger-spec.md](archive/p2p-messenger-spec.md)). Этот файл — **порядок
и зависимости** работ. Сквозная картина системы — в [ARCHITECTURE.md](ARCHITECTURE.md).
Концептуальный индекс (подсистемы → фичи, хребет для кода/плана/UI) —
в [SUBSYSTEMS.md](SUBSYSTEMS.md).

## Принципы
- Полный P2P, без своего сервера для данных (единственное внешнее — push-пробуждение).
- E2E-шифрование; для медиа конфиденциальность даёт транспорт Yggdrasil.
- **Эффективность без потери качества** (минимум аллокаций/копий/оверхеда; цель — 1080p60 + чёткий звук, без экономии на битрейте).
- Общее Rust-ядро (`core`/`transport`/`messenger`/`media`) переиспользуется всеми платформами. Десктоп (Slint) — эталонная реализация; Android — порт поверх того же ядра.

## Готово
- [x] Идентичность (ed25519 → Yggdrasil/Curve25519/BIP39), персистентность.
- [x] Транспорт Yggdrasil через FFI (без TUN/root), вход в глобальную сеть.
- [x] E2E-чат: протокол, NaCl Box, сессии, presence, keepalive, повтор до Ack.
- [x] Контакты (TOFU) + история сообщений на диске, at-rest шифрование (vault).
- [x] Десктоп-UI на Slint (контакты/чат/мой код/инфо/звонки/группы/настройки), Holo-тема.
- [x] Лёгкий медиа-транспорт (демукс чат/медиа, бинарное обрамление, без Ack/крипто на пакет).
- [x] Аудио-кодек Opus + джиттер-буфер; сквозная проверка на синтетике.
- [x] 1:1 аудио-звонки (cpal), 1:1 видео (H.264, камера/экран).
- [x] Групповой чат (MLS, serverless), групповые звонки (full mesh).
- [x] Android: JNI-мост, чат, 1:1 звонки, групповой чат, MediaCodec H.264.
- [x] Foreground service (Android): WakeLock + WifiLock, держит mesh живым.
- [x] Аудит безопасности (ядро + десктоп): все High/Medium/Low закрыты.
- [x] H1.0: комнаты-звонки — маячок присутствия (Discord-style), instant leave, TTL.
- [x] H1.1: мультипати аудио комнат (mesh multicast + audio mix, routing по участникам).
- [x] Адаптивный джиттер-буфер + устойчивое декодирование видео (динамическая глубина по наблюдаемому джиттеру, pendingPacket-retry в декодере).
- [x] QoS транспорта: приоритетные write-очереди в ygg.go (audio/chat blocking, video drop-on-full).

### Android — доработки после теста на железе (2026-06-15)
- [x] Видеозвонок зависал: YUV→RGB в Kotlin (65.8% CPU) → перенесён в Rust (5.2%).
- [x] Нельзя вернуться в звонок: invite от того же пира = переприглашение.
- [x] MediaCodec (аппаратный H.264): zero-copy через input-surface, 518/800% CPU idle.
- [x] Потоковая архитектура: UI больше не зовёт Native напрямую (poll/ticker/ops).
- [x] Видео фризило: камера пинится на фиксированный fps; FPS-диапазон в миллигерцах (Qualcomm) тоже обрабатывается.
- [x] Аудио не чёткое: декод перенесён в pull_audio (ровный темп потребителя).
- [x] Аудио зациклилось: PLC-счётчик, тишина после MAX_PLC=3 (~60мс).
- [x] UI-оверхол: иконки (vector drawables / Material icons), единые размеры/отступы.
- [x] Сессионная архитектура JNI: `Session`-объект вместо `static CALL/APP/ROOM_CALL`; несколько комнат одновременно, deadlock-риск снижен.
- [x] Адаптивный джиттер-буфер: глубина регулируется по наблюдаемому сетевому джиттеру; backlog-cap `depth+2` предотвращает накопление задержки.
- [x] Видео 720p@2 Мбит/с; `MAX_VIDEO_CHUNK` 8 КБ (~25 фрагментов/кадр вместо ~160) — меньше cgo-оверхед.
- [x] QoS транспорта (ygg.go): `reliableCh` (аудио + чат, blocking) и `videoCh` (video/screen, try-send); writerLoop всегда дренирует reliable-очередь первой.

### Android — энергопотребление (2026-06-24)
Постоянный mesh-узел («режим A») жрёт батарею даже вне звонка: `ConnService`
держал PARTIAL_WAKE_LOCK + Wi-Fi FULL_HIGH_PERF всё время жизни процесса.
- [x] Wi-Fi FULL_HIGH_PERF убран из фона; high-perf (LOW_LATENCY) берёт
  `CallService` только на время звонка. CPU-wakelock остаётся (узел жив в фоне).
- [x] Троттлинг поллинга в фоне: poll 80→400мс, ticker 3→15с (в звонке 2с).
- [x] Кнопка «Отключить» в уведомлении соединения → стоп `ConnService` (локи
  отпускаются, CPU спит); вход в приложение (`onStart`) поднимает заново.
- [ ] **Экран настроек соединения/энергии (Android):** пользовательский контроль
  над «режимом A»: вкл/выкл постоянного узла, удержание CPU-wakelock, политика
  Wi-Fi-лока, интервалы поллинга/маячков, расписание «онлайн-часов». Сейчас
  выбор захардкожен; нужно отдать его юзеру (вместе с «Экран настроек медиа»).

## Фаза H — Глобальный редизайн «Telegram + Discord» (Android-first)

Крупный разворот продукта (решено 2026-06-15). Не «переписать всё разом», а по
ФУНДАМЕНТАМ, держа приложение рабочим. Бóльшая часть желаемых фич сводится к 4
переиспользуемым подсистемам.

**Зафиксированные решения:**
- **Комнаты звонков = MLS-группы + маячок присутствия** (переиспользуем готовую
  крипту/членство MLS и десктопный mesh `GroupCall`).
- **UI = плавающее окно поверх других приложений** (Android PiP/bubble или
  draw-over-apps) + единый тёмный компактный стиль.
- **Офлайн-доставка = чисто serverless** (очередь на диске + фоновый флаш по
  присутствию; foreground-сервис расширяет окна пересечения).
- **Сначала Android**; ядро/протоколы общие, десктоп догоняет.

### H1 — Постоянные комнаты (звонки как в Discord)

- [x] **H1.0 — Маячок присутствия:** подписанный периодический сигнал «я в комнате
  R, аудио/видео вкл» членам группы. RoomPresence в протоколе. Комната жива, пока
  в ней ≥1 участник; хост не нужен; зайти можно в любой момент.
- [x] **H1.0 — Instant leave:** сигнал «я вышел» (PRESENCE_LEFT flag) → участники
  убирают мгновенно, не ждут TTL.
- [x] **H1.0 — TTL 5s:** участники без свежего маячка считаются вышедшими.
- [x] **H1.0 — Sub-second appear:** beacon отправляется сразу при join, не ждёт
  интервала → участники видят нового за <1с.
- [x] **H1.1 — Мультипати аудио комнат:** mesh multicast захвата живым участникам
  (sync_room_members каждые 2с), приём по источникам с отдельным джиттер/декодером
  на отправителя, микс аудио в выходное кольцо. RoomCallEngine в androidjni.
- [ ] **H1.2 — Видео в комнатах:** мультикаст видео от участникам (как аудио), сетка
  участников в UI (Compose: per-participant SurfaceView/декодер).
- [ ] **H1.3 — Собственное превью, фронт/тыл:** переключение камеры, отображение
  своего видео в оверлее.
- 1:1 становится комнатой на двоих (текущая модель invite/accept-only уходит;
  частный случай — F1-фикс возврата в звонок).
- Сюда же: P1 аспект SurfaceView, P2 своё превью, P3 фронт/тыл.

### H2 — Контент-адресные блобы (фундамент медиа)

- Чанками, адресация по хэшу (BLAKE3), pull-запрос «дай блоб X», возобновляемо,
  лимиты размера/типа (анти-DoS). Прямая тяга с устройства собеседника.
- Первый потребитель — **аватарки** (периодическая сверка хэша → тяга при смене).
- Готовит H5 (картинки/видео/файлы/превью) почти бесплатно.

### H3 — Присутствие + офлайн-очередь сообщений (serverless)

- Очередь исходящих на диске; фоновый флаш по событию «пир в сети». Усиление
  текущего reliable-слоя поверх готового foreground-сервиса.

### H4 — UI-оболочка

- Плавающее окно поверх (overlay/PiP) для звонка; единый тёмный «оверлейный» стиль.
- Пере-оформляем экраны по мере готовности H1–H3. Сворачивает старый UI-оверхол.

### H5 — Богатые сообщения (потом)

- Картинки/видео/файлы (на H2), markdown, превью ссылок. Полировка «как в телеге».
- *Отложено (2026-10-22):* время отправки в сообщении. Сейчас входящее получает время
  приёма, и досланное после долгого офлайна показывает время доставки. Если делать —
  `sent_at` внутри зашифрованного payload и **только для показа** («отправлено вчера
  21:40», если расходится с приёмом больше чем на несколько минут); время из будущего
  обрезать до времени приёма. Сортировку не трогать: чужие часы могут врать, а время
  можно подделать и закопать сообщение в истории. Сетевое время (NTP) не нужно —
  против serverless, а часы телефона и так синхронизирует ОС.

### H6 — Аудит безопасности + багфикс-проход

- Новая поверхность: блобы (untrusted-контент, парсеры/CVE, DoS размером),
  комнаты (авторизация входа), overlay-разрешения. Повторить скан зависимостей.
- **Вход:** доп-аудит крипто-слоя 2026-07-02 уже дал находки SEC-1…SEC-5
  ([security-audit](architecture/security-audit-2026-07-02.md),
  [threat-model](architecture/threat-model.md)); SEC-1/SEC-2 адресуются в E4/[ADR-004].

**Порядок:** H1 → H2(+аватарки) → H3 → H4 (оформляем по ходу) → H5 → H6.

## Верификация — лестница от дешёвого к дорогому

Не «формальная верификация» одним куском, а **слои**: разные инструменты ловят
разные баги. Часть начинаем РАНО (дёшево, работает как тесты), часть — post-1.0,
на стабильных контрактах. Цель — чтобы код/протокол перестали быть слабым звеном
(см. модель угроз: атаковать должно быть дешевле через ОС эндпоинта, не через нас).

**Слой 1 — рано, низкий порог (можно до 1.0):**
- **Фаззинг (`cargo-fuzz`/libFuzzer) + property-тесты (`proptest`)** на парсерах
  недоверенных байт из сети — самая опасная поверхность: `parse_video_frag`,
  сборка фрагментов, разбор presence/маячков, разбор MLS-сообщений. Coverage-guided
  фаззинг ловит краши за часы при минимуме настройки. **Лучший ROI — начинать
  отсюда.** Цель: «парсер не паникует/не мисиндексит ни на каком входе».
- **MIRI** на `unsafe`-участки (UB-детектор), если есть unsafe.

**Слой 2 — Kani (bounded model checking Rust-кода), в CI:**
- [Kani](https://model-checking.github.io/kani/) (поверх CBMC) — символьная проверка
  САМОГО кода на символьных входах до границы N: паники, переполнения, выход за
  границы, `unwrap` на `None`, наши `assert`-ы. Харнессы `#[kani::proof]` на 2-3
  самых критичных парсера; они же работают как сильные тесты.
- Честные пределы: bounded (неограниченные циклы/рекурсию полностью не докажет),
  тормозит на сложном коде (state explosion), проверяет ТОЛЬКО написанные харнессы,
  НЕ проверяет крипто-математику и НЕ пересекает FFI/JNI/Go-часть.

**Слой 3 — TLA+ модель распределённого протокола (post-1.0):**
- Инварианты, на которые нельзя полагаться «по тестам» (распределённые отказы:
  партиции, гонки, эквивокация — см. «Согласованность и отказы» в
  [SUBSYSTEMS.md](SUBSYSTEMS.md)): порядок групповых сообщений (DAG из
  [ADR-002](adr/ADR-002-group-message-ordering.md)) — сходимость и одинаковый
  детерминированный итоговый порядок у всех; presence/членство комнаты; офлайн-
  очередь (без потери/дублей, идемпотентность). Model-check: БЕЗОПАСНОСТЬ (никто
  не расходится, сообщение не теряется) + слабая ЖИВОСТЬ (доставка при возврате
  связи). Проверяет МОДЕЛЬ дизайна, не реализацию.

**Слой 4 — крипто-протокольная логика (НАША обвязка, не примитивы):**
- Анти-replay, обработка MLS-эпох, обёртка ключей (DEK + защита). Символьная
  проверка протокола — **Tamarin/ProVerif** (секретность, аутентификация). Сам MLS
  академически уже верифицирован — проверяем СВОЮ композицию вокруг него, а не его;
  примитивы (NaCl/openmls) тоже считаем вычитанными.

Почему слои 3-4 — post-1.0: дорого и имеет смысл лишь на стабильных контрактах.
Продолжение линии H6 (аудит), но на уровень глубже. Слои 1-2 — начинать раньше.

## Кросс-секущие решения (зафиксированные)

- **Крейт `call`** — оркестрация звонка (сигнализация + аудио/видео-треки) поверх
  `messenger` + `media`. Один автомат на 1:1 и групповые звонки.
- **Согласование кодеков** — в `CallInvite/CallAccept` (offer/answer-lite по
  надёжному каналу), затем медиа течёт.
- **Формат фрагментации видео** — frame_id/frag_idx/marker; аудио и видео делят один
  медиа-канал.
- **Десктоп — эталон**; Android начинается, когда контракты ядра устаканились.

## Порядок по умолчанию

A → B → C → D → E → G, затем H1 → H2 → H3 → H4 → H5 → H6. Фаза F — независимо.
Верификация — лестницей: фаззинг/proptest + Kani на парсеры начинать РАНО (до 1.0);
TLA+ протокола + Tamarin/ProVerif крипто-обвязки — post-1.0, на стабильных контрактах.
