# Релизы и обновления

Как выпускается версия Peerage и как телефон узнаёт о новой. Скрипт — `scripts/release.sh`;
подпись — `scripts/lib/sign.sh`; воспроизводимая сборка — [reproducible/README.md](../reproducible/README.md).

## Версия — одна точка

`APP_VERSION` в `android/app/build.gradle.kts`, вид `M.m.p` (числа, `m` и `p` меньше 100).
`versionCode` выводится из неё: `M·10000 + m·100 + p` (0.1.0 → 100, 1.2.3 → 10203). Руками
`versionCode` не поднимается — новый релиз не может уйти с прежним номером, а Android
не ставит обновление с номером не больше установленного.

Тег релиза — `v` + версия (`v0.1.0`). `release.sh` проверяет, что версия на теге совпадает
с тегом и что `versionCode` вырос относительно прошлого тега.

## Как выпустить

1. Поднять `APP_VERSION`, закоммитить, поставить тег и отправить его:
   `git tag v0.2.0 && git push origin master v0.2.0`.
2. `scripts/release.sh v0.2.0` (Git Bash; Docker — в WSL). Скрипт собирает тег в чистом
   контейнере, подписывает релизным ключом (пароль спросит apksigner) и кладёт в
   `dist/v0.2.0/` три файла:
   - `peerage-0.2.0-arm64-v8a.apk`
   - `update.json` — манифест обновления (ниже)
   - `SHA256SUMS`
3. Релиз на GitHub для тега: приложить эти три файла, в описание — что нового и отпечаток
   сертификата (скрипт печатает его в конце). До 1.0 релиз отмечается как pre-release.
4. Поставить APK на телефон поверх прежней версии — обновление должно встать без удаления.

Раздаётся только `arm64-v8a`: x86_64 — сборка для эмулятора.

## Ключ подписи

Релизный ключ — не в репозитории: путь в `scripts/local.env` (`PEERAGE_KEYSTORE`,
`PEERAGE_KEY_ALIAS`), пароль — в менеджере паролей. Обновление ставится только поверх
сборки с тем же ключом: **потерянный ключ — конец обновлений**, всем придётся удалить
приложение (вместе с данными) и поставить заново. Поэтому у ключа две копии в разных местах.

Отпечаток сертификата (SHA-256) публикуется в README и в каждом релизе: первая установка
сверяет его руками, дальше сверку делает Android.

## update.json, формат 1

Постоянный адрес последнего манифеста — его отдаёт GitHub:
`https://github.com/peerage-chat/peerage/releases/latest/download/update.json`.
Работает только для обычного релиза: `latest` пропускает pre-release, а бета-релизы (до 1.0)
выходят как pre-release. Пока обычного релиза нет, манифест — по адресу тега,
`…/releases/download/v0.1.0/update.json`; список релизов с pre-release отдаёт API
(`/repos/peerage-chat/peerage/releases`). Проверка обновлений в приложении построена на
API, а не на `latest`.

```json
{
  "format": 1,
  "version_name": "0.2.0",
  "version_code": 200,
  "tag": "v0.2.0",
  "commit": "<40 hex>",
  "date": "2026-12-01",
  "cert_sha256": "<64 hex, без двоеточий>",
  "apks": [
    {"abi": "arm64-v8a", "file": "peerage-0.2.0-arm64-v8a.apk", "size": 52428800, "sha256": "<64 hex>"}
  ],
  "notes": "https://github.com/peerage-chat/peerage/releases/tag/v0.2.0"
}
```

| Поле | Что |
|---|---|
| `format` | Версия формата. Несовместимое изменение — новый номер; клиент, не знающий номера, молчит. |
| `version_name`, `version_code` | Как в APK. Новее установленного — только по `version_code`. |
| `tag`, `commit` | Откуда собрано: по ним APK воспроизводится и сверяется. |
| `date` | Дата коммита (не сборки — сборка воспроизводимая). |
| `cert_sha256` | Отпечаток сертификата подписи. |
| `apks[]` | Файл для ABI: имя ассета в том же релизе, размер, SHA-256. |
| `notes` | Страница релиза. |

Новые поля добавляются без смены `format`; клиент неизвестные поля пропускает.

## Проверка обновлений в приложении

С 0.4.0 (п. 46, `Updates.kt`; интерфейс — app-ui.md → «Обновления»). Правила:

- **Выключена по умолчанию.** Запрос к GitHub раскрывает ему IP-адрес и сам факт
  использования Peerage — мессенджеру, который этого избегает, такой запрос без согласия
  не положен. Тумблер — в настройках, с этим объяснением.
  Согласие спрашивается один раз полосой на главной; дальше — тумблер в «О приложении».
- Источник: `GET https://api.github.com/repos/peerage-chat/peerage/releases?per_page=10` —
  первый релиз с ассетом `update.json` (pre-release тоже), затем
  `…/releases/download/<тег>/update.json` и APK оттуда же по полю `file`.
- Не чаще раза в сутки; ответ с неизвестным `format` — молчание.
- Скачанный APK сверяется до установки: размер и `sha256` из манифеста, и отпечаток
  подписи APK **с отпечатком установленного приложения** (не с полем манифеста: манифест
  можно подделать, ключ — нет). Не совпало — файл удаляется, пользователю — ошибка.
- Установка — системным установщиком; молча приложение ничего не ставит.
- Обрыв — докачка с того же места (`Range`, до 5 попыток подряд; сервер без `Range` — с нуля);
  недокачанное остаётся, «Повторить» продолжает. Файл лежит в `noBackupFilesDir`, не в кэше:
  кэш Android чистит при нехватке места, и сверенный файл пропадал до «Установить».

## Obtainium

Obtainium (менеджер обновлений из GitHub-релизов) работает без доработок:
источник — `https://github.com/peerage-chat/peerage`, фильтр APK — `arm64-v8a\.apk$`.
Версию он берёт из тега, подпись при обновлении проверяет Android.

## Сверка релиза с исходниками

`scripts/repro-build.sh out v0.2.0` собирает неподписанный APK тега; с раздаваемым он
совпадает во всём, кроме подписи — сравнение через `apksigcopier compare`
([reproducible/README.md](../reproducible/README.md)).
