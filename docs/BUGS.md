# Известные баги

## Звонки (видео/аудио) — к разбору 2026-06-25

### Камера
- **[ПРИЧИНА НАЙДЕНА] Чёрный экран: камера не отдаёт видео.** Логи `VideoSender`:
  `Camera opened successfully` → `Camera capture session configuration failed`
  (`onConfigureFailed`). Корень: размер input-surface энкодера (напр. 1920×1080)
  обязан быть из списка поддерживаемых камерой выходных размеров
  (`StreamConfigurationMap.getOutputSizes`). Если камера не поддерживает точный
  запрошенный размер (эмуляторная фронталка не тянет 1080p; многие реальные
  фронталки тоже) → `createCaptureSession` молча падает → видео не идёт, ретрая
  нет. Это и есть «камера часто не стартует» на железе, в обе стороны.
  **План (НЕ авто-подбор):** дать юзеру ОГРАНИЧЕННЫЙ выбор разрешений на основе
  того, что реально поддерживает его камера — перечислить `getOutputSizes` для
  выбранной камеры и показать как пресеты (вместе с «Экран настроек медиа»).
  Энкодер создавать строго под выбранный поддерживаемый размер.
- **[редко] У одной из сторон камера вырубается / картинка пропадает** по ходу
  звонка. Точная причина неизвестна (камера? декодер? обрыв потока?). Лечится
  перезвоном. Нужны логи `VideoSender`/`VideoReceiver` в момент пропажи.

### Сеть
- **[редко] Первый звонок не доходит.** Один раз приглашение не дошло до пира
  (первый звонок после простоя). RoomInvite — fire-and-forget по мешу; если
  пир-соединение не прогрето, пакет теряется без ретрая. Кандидат: ретрай
  приглашения / прогрев соединения перед отправкой invite. Следить, повторится ли.

### Жизненный цикл звонка (комнаты) — ПЛАН СОГЛАСОВАН, не реализован

**Модель (как должно быть):** комната R между двумя — ПОСТОЯННАЯ
(`dm_room_id` детерминирован — это правильно). «Позвонить» = войти в R
(presence + медиа). Ring (приглашение) — лишь уведомление войти, если пир ещё
НЕ в комнате. «Выйти» = убрать своё присутствие; пир ОСТАЁТСЯ в комнате.
**Решение по UX:** при выходе собеседника из 1:1 — остаёмся в пустой комнате
(не авто-завершаем), но надо показать, что ты один → нужна СЕТКА участников
(H1.2). См. [[redesign-direction]].

**Что ломает «комнатность» сейчас (всё связано):**
1. Re-invite выкидывает пира: в `applyEvent` ветка `room_invite` делает
   `if (currentRoom != null && dmCallPeer == peer) leaveRoom()` — если уже в R с
   этим пиром, а он перезаходит, нас рвёт из звонка и показывает промпт.
2. Каскад с decline: этот `leaveRoom()` (после фикса отмены) шлёт
   `roomDeclineDm` → у перезашедшего `room_decline → leaveRoom` → оба вылетают.
   Это и есть «всё ломается».
3. Отложенный `Job::Leave(R)` от старого выхода затирает `dm_peers[R]` свежего
   перезахода и шлёт ложный LEFT (event_pump в lib.rs).
4. `decline`-на-каждый-выход (фикс отмены) — анти-комнатный: при выходе из
   АКТИВНОЙ комнаты надо слать только presence LEFT, пир остаётся. Decline — лишь
   чтобы погасить ring (пир ещё не вошёл).
5. Зависшая картинка — та же модель: пир шлёт LEFT, ты в комнате, его
   видео-surface не чистится.

**Точечные правки (к реализации):**
- `room_invite` (Model.kt): если уже в R с этим пиром → ИГНОР (остаёмся, его
  возврат покажет presence). Убрать `leaveRoom()` оттуда.
- `Job::Leave(R)` (lib.rs event_pump): no-op, если уже перезашли (`joined`
  содержит R) — иначе сносит свежий dm_peer/шлёт ложный LEFT.
- `leaveRoom` (Model.kt): слать `roomDeclineDm` ТОЛЬКО если пир НЕ присутствует
  (отмена ring); активный выход = только `roomLeave` (LEFT).
- На `room_presence` LEFT пира, чьё видео показываем: остановить его
  `VideoReceiver` + очистить surface (чинит зависшую картинку). С сеткой (H1.2)
  — убрать его тайл.

### Жизненный цикл — ЗАКРЫТО
- **[ИСПРАВЛЕНО] Отмена дозвона не гасила экран входящего.** Коммит: `leaveRoom`
  для DM шлёт `RoomDecline` пиру → гасит `incomingCall`+уведомление. ВНИМАНИЕ:
  при реализации room-модели (пункт 4 выше) это поведение уточняется — decline
  только для отмены ring, не для выхода из активной комнаты.

### Аудио
- **[ЗАКРЫТО — артефакт эмулятора, wontfix] Зацикливание звука в шум.**
  Проявлялось и в фазе дозвона, и рандомно по ходу звонка. Доказано, что наш
  конвейер ни при чём: в дозвоне `playback: 259 starv/5s` (100% голодание —
  источника нет, пишем тишину), а по ходу звонка `playback: 0 starv/5s` на ОБЕИХ
  сторонах (ни одного пропущенного кадра — звук отдаётся корректно). При этом
  AudioFlinger эмулятора сыплет `FAST flag mismatch` / `mixer throttle` — петля
  возникает НИЖЕ нашего слоя, на эмулируемом аудио-HAL. Пользователь подтвердил:
  слышно только на эмуляторе; на реальных телефонах после фикса джиттера звук
  чистый. В прод не едет. НЕ чинить костылём под эмулятор.
  Отдельный (НЕ про шум) законный момент на будущее: `CallAudio` гоняет
  микрофон+playback всю фазу дозвона, когда играть нечего — лишний расход
  CPU/батареи/удержание мика. Чистое улучшение (не костыль): стартовать медиа по
  первому участнику, а не на invite (ценой ~100-200мс задержки на старте).
