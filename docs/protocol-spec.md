# Контракт API движка (Command / Event / Snapshot) — спека v0

**Статус:** черновик, отражает ТЕКУЩУЮ поверхность (2026-06-27) · версия контракта `0`.
Связано: [ADR-003](adr/ADR-003-engine-api.md) (решение), [v1.0-scope](v1.0-scope.md).

> Цель: единственный контракт между движком (Rust) и клиентом (Android/JNI,
> десктоп). Клиент рендерит **Snapshot** и шлёт **Command**; движок асинхронно
> отдаёт **Event**. Домейн-логику клиент НЕ считает. Это формализация уже
> существующих ~40 JNI-вызовов как типизированного контракта; миграция —
> инкрементально (см. ADR-003), первый пример типизации — `NetStats`.

## Принципы
- **Три рода обмена:** `Command` (намерение, может вернуть подтверждение),
  `Query→Snapshot` (синхронное чтение состояния), `Event` (асинхронное уведомление).
- **Версионирование:** поле `protocol_version` (сейчас `0`); эволюция аддитивная —
  новые варианты/поля не ломают старых клиентов.
- **Медиа — отдельный горячий канал.** Поток PCM/H264 (`room_push_*`/`room_pull_*`)
  НЕ заворачивается в типизированный Command/Event (производительность); это
  низкоуровневый byte/short-канал по контракту «push/pull». Описан отдельно.
- **Идентификаторы:** ключи/gid/room_id — hex ed25519/32 байта; время — unix-секунды
  (косметика), тайминги корректности — монотонные внутри движка.

## Где живёт схема

Формы снимков и событий описаны **типами** в `engine/src/dto.rs`, а не литералами
`json!` по месту вызова. Раньше схема существовала в двух экземплярах — сборка JSON в
Rust и разбор по строковым ключам в клиенте, — и переименование поля обнаруживалось
только на устройстве. Теперь `push_event` принимает `dto::UiEvent`, а снимки
собираются из структур; тесты в `dto.rs` фиксируют форму провода дословно, поэтому
несовместимое изменение ломает сборку, а не пользователя.

Формат на проводе при этом не менялся: типы подобраны под уже существующие имена полей.

## Commands (намерение клиента → движок)
Группировка по подсистемам. `→ T` — синхронный возврат.

**Жизненный цикл**
- `Start{data_dir, vault_key} → Me{pubkey,address,fingerprint}` — инициализация сессии.
- `Stop` · `DestroySession` — остановка/освобождение.
- `PollEvent → Event?` — выбрать следующее событие (до перехода на push).

**Контакты (TOFU)**
- `AddContact{key,name} → {added|known|error}`
- `RenameContact{key,name}` · `RemoveContact{key}` · `SetVerified{key,bool}`
- `Connect{key}` — держать фоновое соединение.

**Сообщения 1:1**
- `SendDm{key,text} → msg_id` (≥0 принято к доставке; <0 пир недостижим → офлайн-
  очередь, **репатриация в M3**).

**Группы (MLS)**
- `GroupCreate{name} → bool` · `GroupInvite{gid,key}` · `GroupSendText{gid,text}`

**Комнаты-звонки (присутствие)**
- `RoomInviteDm{key,audio,video} → room_id` · `RoomJoinDm{key,…} → room_id` ·
  `RoomDeclineDm{key}`
- `RoomJoin{gid,audio,video}` · `RoomLeave{gid}` · `RoomSetMuted{bool}`

**Сеть**
- `ReconnectPeers` — форс-реконнект публичных пиров (обход backoff).
- `SetRelay{bool}` *(план M3)* — режим «узел сети».

**Диагностика**
- `BenchRecvStart` · `BenchBlast{key,kb} → stats`

## Snapshots (синхронное чтение состояния)
Движок отдаёт ГОТОВОЕ состояние (агрегаты считает он, не клиент):
- `Me` — {pubkey, address, fingerprint}.
- `Contacts` — [{key,name,fingerprint,verified}].
- `History{key}` — [{id,text,mine,time,status}] (incl. queued-плейсхолдеры).
- `IsOnline{key} → bool`.
- **`NetStats`** — {peer_count, tree, ping_ms, rx_rate, tx_rate, peers:[{key,inbound,
  up,latency_ms,rx_rate,tx_rate,uptime_s}]}. ✅ типизировано (первый пример контракта).
- `Groups` — [{gid,name,members}] · `GroupHistory{gid}` — [{text,mine,time,sender,system}]
  · `GroupMembers{gid}` — [key…].
- **`GroupPresence{gid}`** — {total, online}. ✅ типизировано (агрегат «N уч · M в
  сети» = MLS-ростер ∩ presence, считает движок; презенс динамичен → на момент чтения).
- `RoomParticipants{gid}` / `RoomPresencePeers{gid}` — [{peer,audio,video}].
- `OfflineQueue` *(план M3)* — {count, per_peer…}.

## Events (асинхронно движок → клиент)
- `Presence{peer,online}` — изменение присутствия (триггерит флаш офлайн-очереди).
- `Text{peer,id,text,time}` — входящее 1:1.
- `Ack{peer,id}` / `Undelivered{peer,id}` — статус доставки исходящего (5-мин ретрай
  истёк → Undelivered → офлайн-очередь, **M3**).
- `RoomInvite{peer,room_id,audio,video}` / `RoomDecline{peer,room_id}`
- `RoomPresence{gid,peer,flags|left}` — состав комнаты на лету.
- `GroupsChanged` — состав/список групп изменился (перечитать снапшоты).
- `GroupMsg{gid,text,sender,system}` — входящее групповое (incl. системные строки).

## Медиа — горячий канал (вне типизированного контракта)
Контракт «push/pull» поверх byte/short-буферов, минимум оверхеда:
- Аудио: `RoomAudioStart{gid}→{rate,ch,frame}` · `RoomAudioStop` ·
  `RoomPushAudio{pcm[]}` · `RoomPullAudio→pcm[]`.
- Видео: `RoomPushVideo{au,keyframe}` · `RoomPullVideoPacket{peer}→bytes` ·
  `RoomSetVideoCap{frames}`.
Фрагментация/джиттер/микс — внутри движка (`media`/`androidjni room_call`).

## Анти-abuse (ingress)
- ✅ **Механизм (M1):** receiver-enforced token-bucket на источник
  (`p2p_core::ratelimit::RateLimiter`) в приёмном цикле мессенджера. Применяется по
  Yggdrasil src-ключу **до расшифровки** → флуд дропается до дорогого крипто.
  Раздельные бюджеты: строгий для CHAN_CHAT (спам-вектор), щедрый для CHAN_MEDIA
  (звонок легитимно высокочастотен). Навязывает принимающий → модификация
  отправителя не обходит. Юнит-тесты без устройства. Для меш-источника, который
  нельзя отключить на линк-уровне, исчерпание бюджета = «разрыв сессии» на входе.
- ✅ **Единый бюджет пира (M3):** `p2p_core::budget::Tier` — ОДНА точка, из которой
  выводятся ingress-лимит, cap офлайн-очереди и её TTL (раньше политики жили в пяти
  местах со своими константами):

  | Тир | ingress (burst/сек) | срок хранения очереди |
  |---|---|---|
  | `Blocked` | отказ **до расшифровки** | не храним |
  | `Stranger` | 30 / 10 — **общая корзина класса** | 1 день |
  | `Contact` | 60 / 30 персонально | **бессрочно** |
  | `Verified` | 120 / 60 персонально | **бессрочно** |

  Чужие делят одну корзину на весь класс → Sybil из 1000 ключей не расширяет бюджет.
  Тир вычисляет движок (`refresh_budgets`) из контактов (`verified`) и блок-листа
  гейта; блок сильнее контакта.

  **Очередь исходящих не режется ни по объёму, ни (для контактов) по сроку.** Она
  состоит из СОБСТВЕННЫХ сообщений пользователя: сервера, который сохранит их за нас,
  нет, поэтому и «протухло», и «вытеснено» означают «потеряно навсегда» (собеседник
  вернулся через месяц — обязан получить). Автоматического вытеснения нет вовсе;
  при разрастании клиент **предупреждает** (`OutboxStats::should_warn`, порог 1000),
  а удалить очередь можно только явным действием пользователя (`clear_peer`).
  **Единственное исключение — заказанная пользователем докачка.** Нажав «Скачать», он
  сам попросил у пира поток байт: резать его анти-флуд бюджетом бессмысленно, ведь
  бюджет защищает от НЕЖДАННОГО трафика. `Messenger::boost_peer` снимает ingress-лимит
  адресно (только этот пир) и на срок (`BLOB_BOOST_FOR`, 2 мин, продлевается каждым
  новым запросом). Блокировка сильнее буста: `Blocked` режется раньше проверки.

  Само намерение «скачать» персистентно (таблица `wanted_blobs`): пир может быть офлайн
  или уйти посреди докачки — движок продолжит сам при его появлении (`resume_wanted`)
  и переживёт перезапуск. Следить за тем, когда собеседник появится в сети,
  пользователь не должен.
- ✅ **Репутация (способ 1):** «полезное дело» = пир полностью отдал нам блоб, то есть
  потратил на нас свой трафик. Счётчик `helpful` в контактах поднимает бюджет плавно
  до ×2 (20 дел). Бонус — **только прошедшим гейт** (`Contact`/`Verified`): иначе Sybil
  обошёл бы общую корзину, «помогая» тысячей одноразовых ключей.

### Адрес отдельно от личности; смена адреса (ADR-007)

**Личность (IK)** — ed25519 из seed/мнемоники: на ней fingerprint, QR-верификация,
MLS-credential и запись контакта. Она не меняется никогда.
**Адрес (TK)** — ключ узла Yggdrasil, из которого выводится IPv6. Это расходник:
его меняют, чтобы оборвать чужой флуд.

```
TK_n = Identity::derive_subkey("dev.p2p.transport.v1/" + n)     // BLAKE3-KDF
TK_0 = IK                                                       // эпоха 0
```

Эпоха 0 — сам ключ личности, поэтому установка, где адрес не меняли, ведёт себя в
точности как до разделения; миграции нет. Ключи эпох детерминированы из seed —
восстановление из мнемоники даёт те же адреса, отдельный секрет не хранится.

**Объявление о смене.** Новый адрес рассылается контактам как

```rust
Payload::TransportRotate { id, epoch, transport_pub, sig }
// sig = IK.sign("dev.p2p.transport-rotate.v1" || epoch_be || transport_pub)
```

Получатель применяет его, только если выполнены ВСЕ условия:
отправитель — известный контакт; подпись сходится с его **личностью**; эпоха строго
новее известной. Без первого условия объявление ничем не подкреплено, без второго это
вектор захвата контакта («я новый адрес Алисы»), без третьего перехваченное старое
объявление вернуло бы жертву на брошенный (возможно, флудимый) адрес. Заблокированному
объявление не применяется вовсе.

Доставка надёжная (`id` → retry-until-Ack): контакт, отсутствовавший в момент смены,
обязан узнать новый адрес по возвращении, иначе связь с ним рвётся навсегда. Тех, кого
не застали, движок догоняет по presence.

**Бакет — APP (4 КБ), не CONTROL.** Одна подпись занимает 64 Б, в потолок 256 Б это не
влезает. Побочно вышло лучше: среди прикладных сообщений объявление неотличимо от
обычного текста или картинки, поэтому наблюдатель (и флудер) не видит по проводу
момент, когда жертва уходит на новый адрес.

**Анти-спуфинг с двумя ключами.** Прежнее правило приёма «`from` в конверте обязан
совпадать с `src` транспорта» перестаёт работать, как только адрес ≠ личность. Пакет
принимается, если выполнено любое из:

1. `from == src` — эпоха 0 или незнакомец (в точности прежнее правило);
2. `src` — известный нам адрес этой личности (связка подтверждена ранее принятым
   объявлением);
3. это само объявление, и его подпись связывает `from → src` — самоподтверждающийся
   случай, без которого новый адрес узнать неоткуда: он приходит уже С нового адреса.

После проверки пир **везде** идентифицируется личностью: история, контакты, тир
доверия, блок-лист и события заведены на неё. Иначе смена адреса разъезжает переписку
(входящее пишется под транспортным ключом), а заблокированный уходит из-под блока,
просто сменив ключ.

**Куда шифровать и куда слать — разные ключи.** Тело шифруется ЛИЧНОСТИ получателя
(его X25519 выведен из неё), а датаграмма отправляется на его текущий АДРЕС.
Перепутать нельзя ни в одну сторону: зашифруешь адресу — получатель не расшифрует,
пошлёшь на личность — пакет уйдёт на покинутый ключ.

**Код обмена (QR / «скопировать ключ»).** До ротации — прежний голый hex личности,
поэтому старые коды и сканеры продолжают работать. После — расширенная форма:

```
<личность-hex>:<эпоха>:<адрес-hex>:<подпись-hex>
```

Подпись здесь та же, что в объявлении, и она обязательна: код часто пересылают через
третьи руки (переписка, форум), и без подписи посредник подменил бы адрес, оставив
личность настоящей.

**Группы это переживают без изменений:** членство MLS ведётся по личностям, а адрес
резолвится в единственной точке отправки, поэтому участник может сменить адрес, не
пересоздавая группу.

**Чего смена адреса НЕ даёт.** Она обрывает поток флудера только вместе с паузой
офлайн (замерено: при мгновенном перезаходе новый узел наследует маршрутную позицию
старого ключа и получает ~88 % потока; после ~30 с офлайна старый ключ выпадает из
дерева и слать на него становится некуда). Границы — в
[threat-model](architecture/threat-model.md) N8 и
[ADR-007](adr/ADR-007-identity-transport-key-split.md).

### Подпись к вложению

Подпись едет **внутри** `Payload::Media` (поле `caption`), а не отдельным текстовым
сообщением. Иначе «фото с подписью» — это два пакета подряд, и наблюдатель узнаёт их
по характерной паре, хотя каждый по отдельности неотличим от текста. Длина режется на
отправляющем слое до `MAX_CAPTION` (1 КБ), чтобы медиа-сообщение оставалось в бакете
APP 4 КБ; резать в UI недостаточно — другой клиент мог бы не резать.

В группах то же самое: поле `caption` в `AppMsg::Media` (тело шифруется MLS и едет тем
же `CHAN_CHAT`), потолок общий.

### Отправка крупных вложений потоком

Манифест крупного файла считается **потоково** (`p2p_blob::manifest_of_file`): файл
читается по одному чанку, хэши и общий id накапливаются на лету. Чанки при отдаче
читаются с диска по индексу (`read_file_chunk`), своя копия пишется в тот же
чанкованный зашифрованный формат, что и принятые блобы. Итог: отправка файла на
гигабайт не требует гигабайта RAM ни на одной стороне — приёмная сторона потоковая
с M2, отправляющая теперь тоже.

В группах то же самое: `group_send_media_file` считает манифест потоково и кладёт свою
копию чанками. Байты при этом уезжают участникам ТОЛЬКО если вложение мельче
`AUTO_DOWNLOAD_LIMIT`; крупное каждый участник запрашивает сам по кнопке. Иначе один
человек с видео на 800 МБ решал бы за всю группу, потратят ли остальные трафик.

Чтобы это было возможно, `AppMsg::Media` несёт метаданные карточки — `size`,
`duration_ms`, `width`/`height` и `thumb` (hex отдельного блоба-миниатюры). Превью
уезжает всем сразу: оно мелкое, и без него предложение «скачать 800 МБ» слепое.

Исключение — картинки: им нужен `scrub` (EXIF/GPS), а он требует всего файла в
памяти. Картинки весят немного, поэтому идут прежним путём.

## Анти-трафик-анализ: размерные бакеты (M5)

Наблюдатель на пути (A1) видит размер зашифрованной датаграммы. Чтобы размер не
выдавал ТИП сообщения, plaintext добивается до бакета **до** шифрования
(`core/src/pad.rs`, формат `[len: u32 BE][content][нули]`; `bucket_for` в
`core/src/protocol.rs`):

| Бакет | Размер | Что попадает | Что скрывает |
|---|---|---|---|
| CONTROL | 256 Б | `Ack`/`Ping`/`Pong`/`RoomPresence`/`Hello`, **`RoomInvite`/`RoomDecline`**, key-request, resync/leave, blob-request | начало звонка неотличимо от ack/ping |
| APP | 4 КБ | `Text`, **`Media`**, `Group`, `GroupInvite`, `GroupKeyReply`, `ProfileUpdate`, `BlobManifest` | картинка/голосовое/файл неотличимы от текста; длина текста и имя файла скрыты |
| CHUNK | 25 КБ | `BlobChunk` | остаток последнего чанка (точный размер файла) |

`unpad` читает длину из префикса и не зависит от бакета → изменение бакетов
**совместимо в обе стороны** со старыми клиентами. Конверт с hex-оверхедом остаётся
ниже датаграммы 65535 (тест `padded_blob_chunk_fits_datagram`).

**Границы (честно, см. [threat-model N7](architecture/threat-model.md)):** скрыт
только размер. Тайминг и частота пакетов, объём (число чанков) и **открытый первый
байт канала** (`CHAN_CHAT` / `CHAN_MEDIA`) — видны. Байт канала оставлен намеренно:
демукс и ingress-бюджет обязаны работать до расшифровки (иначе флуд заставляет
жертву тратить крипто на каждый пакет), а факт звонка всё равно выдаёт тайминг
(~50 пакетов/с). Cover-traffic (постоянный фон) в 1.0 не делаем — цена батареи.

## Заявка о транзите в маячке присутствия (резерв, ADR-008)

`Ping`/`Pong` несут необязательное поле `transit` типа `TransitClaim`
(`digest` — BLAKE3 пачки квитанций, `count`, `epoch`). **В 1.0 оно всегда пусто, не
сериализуется и не читается приёмной стороной.**

Зачем заведено заранее: привилегии за ретрансляцию (приоритет очереди, длинный TTL)
нельзя выдавать по самоотчёту — код открыт, и ретрансляцию несложно вырезать, оставив
флаг. Честная схема — квитанции, подписанные получателем
([ADR-008](adr/ADR-008-proof-of-transit.md)), — реализуется после 1.0, но МЕСТО под
неё обязано быть готово сейчас: маячок присутствия должен остаться в бакете
CONTROL 256 Б, а одна квитанция в hex-JSON (~200 Б) туда уже не влезает. Поэтому в
маячке едет только дайджест пачки, а сами квитанции запрашиваются отдельно.

Тесты, удерживающие это свойство (`core/src/protocol.rs`):
`presence_with_transit_claim_stays_in_control_bucket` — маячок с ЗАПОЛНЕННОЙ заявкой
равен по размеру `Ack`; `empty_transit_field_is_absent_on_the_wire` — пустое поле не
меняет байты на проводе.

## Пересылка сообщения

`Payload::Text` и `Payload::Media` несут `fwd_from` — **hex-ключ автора ИСХОДНОГО
сообщения** (пусто — сообщение своё; пустое поле не сериализуется, байты 1.0 не
меняются). В группах то же поле есть у `AppMsg::Text` и `MediaBody`.

Едет именно ключ, а не готовая строка «переслано от Ани»: имя рисует клиент по
СВОИМ контактам, поэтому подписью нельзя соврать — незнакомый ключ покажется
обрезанным hex, а не чужим именем.

Пересылка пересланного сохраняет ПЕРВОГО автора, а не посредника (тест
`forwarding_keeps_the_original_author`). Вложение пересылается только если его байты
есть у пересылающего: иначе получателю было бы некуда идти за содержимым.

**Приватность — выбор пересылающего.** По умолчанию пересылка раскрывает адресату
автора оригинала: без источника она превращается в пересказ, которому нельзя верить.
Но у пересылающего есть флажок «скрыть автора» — тогда на провод уходит `fwd_anon`
без `fwd_from`, то есть **ключ автора не отправляется вовсе**. Получатель видит
«переслано» без имени: сообщение не выдаётся за своё, но и источник не назван.
Своя копия у пересылающего сохраняется в том же виде, что ушла адресату, — показывать
себе имя, которого собеседник не получил, значило бы расходиться с реальностью
(тест `hidden_forward_sends_no_author_at_all`).

## Закреплённое сообщение

`Payload::Pin { id, target, target_mine, on }` — закрепить (`on = true`) или открепить
сообщение в личном чате. Ссылка на сообщение — пара «автор + id» (ADR-006), «чьё»
едет с точки зрения ОТПРАВИТЕЛЯ и переворачивается на приёме, как у ответа. Бакет
CONTROL: по размеру неотличимо от ack. Доставка надёжная — закреп, сделанный пока
собеседник офлайн, обязан доехать позже, иначе у двоих будут разные шапки одного чата.

**Закреп — свойство ЧАТА, а не того, кто его поставил.** Иначе «закрепил важное»
означало бы «закрепил у себя», и вторая сторона об этом не узнала бы.

В группах то же самое — `AppMsg::Pin { target, sender, on }` внутри MLS. Право
закреплять есть **только у админа** (ADR-004), и проверяется оно на ПРИЁМЕ, по ключу
админа из локального состояния: доверять флагу отправителя нельзя, клиент можно
пропатчить. Поэтому участник теперь помнит не только «админ ли я», но и КТО админ
(`groups/group_admins.json`): создатель группы, а для вступивших — пригласивший.

Хранится закреп в отдельной таблице `pinned` (чат, вид, id, автор, время, кем), а не
флагом в строке истории: его ставит и снимает другой человек, и он должен переживать
удаление сообщения у себя.

## Ответ и отзыв сообщения (ADR-006)

`Payload::Text` несёт `reply_to` (id цитируемого; 0 — обычное сообщение) и
`reply_mine` — **чьё оно с точки зрения ОТПРАВИТЕЛЯ**. Получатель переворачивает флаг:
его «моё» для нас «его». Ссылка — пара «автор + id», потому что id посеян временем
отправителя и у обеих сторон может совпасть; без флага ответ на своё и ответ на чужое
были бы неразличимы. Текст цитаты по проводу НЕ едет: он берётся из локальной истории,
поэтому удаление оригинала не оставляет расходящейся копии.

`Payload::Retract { id, target }` — просьба удалить НАШЕ сообщение `target`
(«удалить у всех»); `id` даёт надёжную доставку, поэтому просьба доедет и после
офлайна. Получатель удаляет строку `(peer = отправитель, id = target, mine = false)` —
то есть чужое сообщение отозвать нельзя (тест
`retract_cannot_touch_someone_elses_message`). Бакет — CONTROL: отзыв неотличим по
размеру от ack. **Граница честная:** это просьба, а не гарантия — собеседник мог
прочитать сообщение раньше, снять экран или использовать патченый клиент, и UI обязан
говорить это прямо.

**В группах то же самое, но ссылка — пара «автор + id»** (собеседников много, флага
«моё/чужое» мало). Прикладное тело группы (`AppMsg`, шифруется MLS) получило
`id`/`reply_to`/`reply_sender` у текста, `id` у медиа и новый вариант `Retract{target}`.
id посеян временем в МИЛЛИсекундах: уникальность нужна только в пределах отправителя,
а секунд не хватало бы — два сообщения подряд получили бы один id.

Автор отзыва берётся ИЗ MLS, а не из тела пакета: иначе участник стирал бы чужие
сообщения, подставив чужой ключ (тест `group_retract_ignores_foreign_messages`).
Сообщения старых клиентов приходят с `id = 0` — на такие нельзя ни ответить, ни
отозвать: сослаться не на что, и UI их не даёт выделить.

## Файл резервной копии данных (`.p2pbak`)

Не сетевой формат, но такой же долгоживущий контракт: файл, созданный сегодня, обязан
открываться будущими версиями. Реализация — `core/src/backup.rs`, состав —
`engine/src/backup.rs`.

```text
"P2PBAK" | version u8 | kdf_profile u8 | salt[16]
кадр*:   len u32 LE | nonce[24] | ciphertext(XChaCha20-Poly1305)
```

* **Кадры, а не единый блоб** — вложения бывают гигабайтами, и держать копию в памяти
  телефона нельзя. Открытый текст кадра: `[kind u8][payload]`, где `0` — JSON-запись
  (манифест / контакты / сообщения / звонки), `1` — блоб (`[id_len][id][bytes]`),
  `2` — конец.
* **Номер кадра в AAD + обязательный кадр-конец.** Каждый кадр аутентичен сам по
  себе, но их ПОРЯДОК и ПОЛНОТА — нет: без этого держатель файла мог бы переставить
  или отрезать куски (например, вырезать часть переписки), не зная пароля.
* **`kdf_profile`** — номер профиля стоимости Argon2id (`core/src/kdf.rs`). Лежит В
  ФАЙЛЕ, потому что стоимость обязана расти вслед за железом, а ключ с другими
  параметрами — другой ключ: без записанного профиля первое же повышение сделало бы
  все ранее снятые копии нечитаемыми, показав «неверный пароль» на верном пароле.
  Хранится НОМЕР, а не сами числа: числа из файла — это ввод, и «память 4 ГиБ»
  положила бы приложение ещё до проверки пароля.
* **Ключ — из пароля, а не из хранилища.** Файл по смыслу уезжает с устройства и
  обязан открываться там, где Keystore этого телефона недоступен.
* **Потолок кадра 16 МиБ** (вложения крупнее 15 МБ в копию не входят и считаются
  отдельно) — защита от файла, заявляющего гигабайтный кадр.

Что НЕ входит в файл: ключ личности (отдельная копия — 24 слова), MLS-состояние групп
(устаревший ратчет ломает группу), транспортные ключи контактов (протухают), признак
верификации (см. threat-model N10).
