# LiteRTC против WebRTC: что берём

Разбор к [ADR-014](../adr/ADR-014-litertc.md), 2026-10-28. WebRTC — это не один протокол, а
стек из десятков RFC и большой реализации (libwebrtc). Ниже его функции по слоям: как они
устроены там, что есть у нас сейчас и что предлагается для LiteRTC.

**Решения (предложение, ждёт владельца):**

| Знак | Значит |
|---|---|
| **P1** | берём в первую очередь: без этого звонки сыплются или есть дыра |
| **P2** | берём следом: заметное качество, но звонки работают и без него |
| **P3** | позже, после беты или после измерений |
| **🔁** | у нас это уже решено другим слоем (Yggdrasil, сессии, движок) — не нужно |
| **✖** | не берём |
| **✅** | уже есть и годится |

Где живёт: **L** — крейт LiteRTC, **К** — кодек (`media`, MediaCodec), **Д** — движок,
**П** — платформа (Kotlin), **С** — сигнализация комнат.

## 1. Связь и шифрование

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| ICE, STUN, TURN, trickle ICE, ICE restart | собирает кандидатов (адреса), пробивает NAT, при неудаче — ретранслятор TURN | Yggdrasil маршрутизирует по ключу, NAT решают пиры меша, «ретранслятор» — сами узлы меша | 🔁 |
| Consent freshness (RFC 7675) | периодически проверяет, что собеседник ещё согласен принимать, иначе прекращает слать | маячки комнаты + фильтр участников: ушедшему не шлём | 🔁 |
| mDNS-кандидаты | прячут локальный IP от веб-страницы | собеседник видит адрес Yggdrasil, а не IP (кроме прямого пиринга) | 🔁 |
| DTLS + DTLS-SRTP | рукопожатие и вывод ключей для медиа, отпечаток сертификата в SDP | сессия 1:1 ADR-012: Noise + ML-KEM, личность из рукопожатия, отдельный ключ медиа (SEC-4) | 🔁 у нас сильнее: постквантовое |
| SRTP/SRTCP | шифрует полезную нагрузку, **заголовок RTP открыт** (seq, метка времени, SSRC видны сети) | шифруется весь внутренний заголовок; снаружи только байт канала | 🔁 у нас лучше; в WebRTC это чинит лишь поздний cryptex (RFC 9335) |
| Окно повторов, смена ключей | счётчик пакетов, перевыпуск ключа | `ReplayWindow` и пересоздание сессии по сроку/числу пакетов | ✅ |
| SFrame / Insertable Streams | E2E-шифрование поверх SRTP, когда медиа идёт через сервер (SFU) | сервера нет, каждая пара шифрует сама | P3: понадобится только вместе с ретранслятором; ключи — из MLS |
| BUNDLE, rtcp-mux | всё медиа и управление по одному порту | байт канала + байт трека | 🔁 |
| SDP offer/answer (JSEP), трансиверы, перепереговоры | текстовое описание возможностей и потоков, обмен до звонка | приглашение в комнату и маячки с флагами аудио/видео | ✖ сам SDP. **Но обмен возможностями нужен** — см. раздел 9 |
| DataChannel (SCTP поверх DTLS) | надёжные и ненадёжные сообщения рядом с медиа | надёжный `CHAN_CHAT` и блобы | 🔁 |
| DTMF (RFC 4733) | тональный набор для телефонии | — | ✖ |

**Итог раздела:** весь этот слой WebRTC существует, чтобы связать два браузера через
интернет без доверенной инфраструктуры. У нас его делают Yggdrasil и сессии, причём
шифрование заголовков и постквантовое рукопожатие у нас уже сильнее.

## 2. Пакеты медиа (RTP)

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Номер пакета (seq) | 16 бит на поток | 16 бит на трек | ✅ |
| Метка времени | время захвата в часах кодека (48 кГц звук, 90 кГц видео) | звук — счётчик сэмплов; **видео — всегда 0** | **P1 L**: настоящее время захвата у видео |
| SSRC (идентификатор потока) | случайный номер потока; новый поток — новый SSRC | нет; перезапуск потока угадываем эвристикой (`STALE_WINDOW`) | **P1 L**: случайный номер потока при каждом старте отправки |
| Marker bit | последний пакет кадра | число фрагментов в каждом фрагменте | ✅ |
| Упаковка H.264 (RFC 6184: FU-A, STAP-A) | режет кадр по границам NAL-блоков, SPS/PPS кладёт рядом | режем кадр вслепую на куски по 8 КБ, SPS/PPS приклеены к ключевому кадру | ✅ пока. **P3**: подобрать размер куска по измерениям (потеря куска = потеря кадра) |
| Упаковка Opus (RFC 7587) | один кадр Opus в пакете | так же | ✅ |
| Расширение: поворот видео (CVO) | поворот в заголовке пакета | **два скрытых байта внутри данных**, понимает только Kotlin | **P1 L**: поворот и fps — в протокол |
| Расширение: сквозной номер пакета (transport-wide seq) | один счётчик на все потоки, нужен для оценки полосы по задержке | нет | **P1 L** |
| Расширение: уровень звука (RFC 6464) | громкость кадра в заголовке: «кто говорит» без декодирования | громкость считаем после декодирования | P2 L: дёшево, нужно для «последних N говорящих» в больших группах |
| Расширение: playout-delay | отправитель подсказывает допустимую задержку (звонок против трансляции экрана) | — | P3 вместе с трансляцией экрана |
| Расширения simulcast/SVC (MID, RID, Dependency Descriptor, layers allocation) | описывают слои и потоки для сервера | — | ✖ пока нет simulcast/SVC |
| Content type, color space | подсказки декодеру и отрисовке | — | ✖ |

## 3. Обратная связь (RTCP)

Сейчас от получателя к отправителю **не идёт ничего**. Это главный пробел.

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Sender Report (SR) | соответствие метки времени потока и настенных часов + счётчики отправленного | нет | **P1 L**: нужен для синхронизации губ и RTT |
| Receiver Report (RR) | доля потерь, всего потеряно, джиттер, данные для RTT | нет | **P1 L** |
| NACK (RFC 4585) | «перешли пакеты N…M» | нет | **P1 L** |
| PLI | «пришли ключевой кадр» | `requestKeyframe()` есть в Kotlin, но по сети его никто не просит | **P1 L** |
| FIR (RFC 5104) | то же, «жёстче» (новый участник) | — | 🔁 сливаем с PLI |
| Transport-wide feedback | время прихода каждого пакета → отправитель сам оценивает полосу | нет | **P1 L** |
| REMB | получатель сам оценивает полосу и сообщает число (устарело в пользу предыдущего) | — | ✖ |
| XR, SDES, LNTF | расширенные отчёты, имена потоков, уведомления о потерях | — | ✖ |
| BYE | «я ушёл» | маячок выхода из комнаты | 🔁 |

Обратная связь пойдёт по `CHAN_MEDIA`: она в реальном времени и терпит потери.
Подтверждения на надёжном канале дали бы лавину, которую запрещает инвариант 2.

## 4. Восстановление после потерь

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| RTX (RFC 4588) | перепосылка по NACK отдельным потоком, чтобы оценка полосы её учитывала | нет | **P1 L**: ограниченная история отправленного, перепосылка одному просившему, потолок доли перепосылок |
| Пропуск до ключевого кадра | кадр, чья опора потеряна, в декодер не отдают, просят ключевой | битые кадры уходят в декодер → картинка размазана до ключевого раз в секунду | **P1 L** |
| Ключевой кадр по запросу вместо периодического | периодических почти нет | каждую секунду (`KEY_I_FRAME_INTERVAL = 1`) | **P1 П** после NACK/PLI: раз в ~10 с + по запросу |
| FEC для видео (ULPFEC, FlexFEC) | избыточные пакеты XOR, восстанавливают потерю без перепосылки | нет | P3: полезно при большом RTT (через меш он бывает 100–300 мс); решать по измерениям |
| RED для звука (RFC 2198) | в каждом пакете повторяется предыдущий кадр звука | нет | P2 L/К: звук мал по объёму, избыточность дешёвая и спасает от пачек потерь |
| Opus in-band FEC | кодек прячет в пакет огрубленную копию предыдущего кадра; **при потере декодер берёт её из следующего пакета** | **кодируем с FEC, но декодер всегда зовётся с `fec = false`** — платим битрейтом и не пользуемся | **P1 К+L**: баг; джиттер-буфер должен отдавать «потерян N, следующий есть» |
| Opus DRED (Opus 1.5) | глубокая избыточность на нейросети, переживает длинные пропуски | — | P3 |
| Opus PLC, нейросетевой PLC (Opus 1.5) | маскировка потери | обычный PLC, после 4 кадров — тишина | ✅ / P3 |

## 5. Полоса пропускания

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Оценка по задержке (GCC: trendline, детектор перегрузки, AIMD) | по времени прихода пакетов видит рост очереди до потерь | нет | **P1 L**. Для нас это важнее, чем для UDP: связи Yggdrasil идут по TCP/TLS/QUIC, перегрузка сначала проявляется ростом задержки, а потери — потом |
| Оценка по потерям | снижает при потерях > ~10 % | нет | **P1 L** |
| Пробы полосы (probing) | короткие всплески, чтобы узнать, выросла ли полоса | нет | P2 L: без них после просадки битрейт поднимается медленно |
| Pacer с приоритетами | равномерная отправка; звук → перепосылки → видео → заполнение | всё сразу: ключевой кадр 4K уходит пачкой | **P1 L**: звук не должен ждать за видео |
| Распределение полосы между потоками | звук фиксирован, видео получает остаток, экран — приоритет | нет | P2 L |
| Подстройка кодера: битрейт, разрешение, fps (quality scaler, degradation preference) | сначала снижает битрейт, потом разрешение или fps | битрейт задан при старте | **P1 П**: команда битрейта; P2 П: лестница разрешений |
| Детектор перегрузки CPU | снижает разрешение, если кодер не успевает | нет | P3 П |
| Сетка (mesh) с одним кодером | — (WebRTC обычно с сервером) | каждому участнику своя копия | ✅ сетка; цель битрейта = минимум по получателям |

## 6. Приём видео

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Буфер кадров с проверкой декодируемости | следит за опорными кадрами, отдаёт только целые цепочки | собираем кадр из кусков; цепочки не проверяем | **P1 L** (вместе с пропуском до ключевого) |
| Оценка джиттера и время показа | фильтр Калмана по размеру кадра и задержке → когда показывать | в Kotlin: подушка из N кадров, темп по fps из скрытого байта | P2 L: перенос в LiteRTC, показ по меткам времени |
| Синхронизация губ | по SR сдвигает задержку звука или видео | нет | P2 L |
| Счётчики фризов | число и длительность заморозок | нет | P2 L (в статистике) |
| Откат с аппаратного декодера на программный | при сбое HW-декодера | нет | P3 П |

## 7. Приём звука (NetEq)

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Адаптивный джиттер-буфер | глубина по статистике задержек | упрощённый: глубина 2–8 кадров по оценке джиттера | ✅ основа есть |
| Растяжение/сжатие времени без смены тона (accelerate, expand) | плавно подстраивает задержку и дрейф часов | глубину меняем выбросом/вставкой кадров | P2 L/К: заметно на слух, но это серьёзная работа (WSOLA) |
| Компенсация дрейфа часов | разные кварцы у телефонов → буфер медленно растёт или пустеет | косвенно, сбросами | P2 (входит в предыдущее) |
| Комфортный шум (CNG) при DTX | шум вместо мёртвой тишины | DTX не включён | ✅ Opus делает сам, если включить DTX |
| Микширование | сумма с ограничителем | сумма с жёстким обрезанием | P3 Д: мягкий лимитер, иначе хрип, когда говорят несколько |

## 8. Обработка звука (APM)

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Эхоподавление AEC3 | своё, одинаковое на всех устройствах | системное Android (`AcousticEchoCanceler`, источник `VOICE_COMMUNICATION`) | 🔁 на Android. Качество зависит от телефона. **На десктопе системного нет** — понадобится своё (P3, отдельный крейт, не транспорт) |
| Шумоподавление, AGC, фильтр низких частот | свои | системные Android | 🔁 на Android; P3 своё (RNNoise-подобное) |
| VAD | определение речи | внутри Opus | ✅ |

## 9. Возможности и согласование

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|
| Согласование кодеков, профилей, уровней (SDP) | стороны договариваются о профиле H.264, макс. разрешении | считаем, что все умеют один профиль H.264 | **P2 С**: короткий обмен возможностями в приглашении и маячке (кодеки, профиль, макс. разрешение/fps декодирования, есть ли HW) |
| Добавить видео посреди звонка | перепереговоры | флаги в маячке | ✅ |
| VP8, VP9, AV1 | несколько кодеков | только H.264 | P3: AV1 сжимает лучше, но аппаратное кодирование на телефонах редкое |

## 10. Групповые звонки

| WebRTC | Как там | У нас | Решение |
|---|---|---|---|

| SFU (сервер-размножитель) | отправитель шлёт один поток, сервер раздаёт | сервера нет | ✖ сейчас. Возможный путь потом — «ретранслятор из участников» + SFrame |

## 12. Безопасность, которой в WebRTC нет или она слабее

| Вопрос | WebRTC | У нас | Решение |
|---|---|---|---|
| **Утечка речи через размер пакетов** | Opus с переменным битрейтом (VBR), размер пакета зависит от звука; WebRTC это не прячет | так же: VBR, без выравнивания | **P1 К**: постоянный битрейт (CBR) или выравнивание размера пакетов звука. Атака на VBR-голос в шифрованном VoIP известна (Wright и др., IEEE S&P 2008). Цена — немного полосы |
| **DTX и ритм речи** | DTX выдаёт, когда человек молчит | DTX выключен (комментарий в `settings.rs` ошибочно говорит обратное) | **P1**: оставить выключенным ради приватности, поправить комментарий. Цена — ~50 пакетов/с в тишине и батарея |
| Флуд до расшифровки | ограничения в браузере | бюджет на источник до расшифровки, по доверию | ✅ |
| Усиление через NACK/PLI | ограничено реализацией | — | **P1 L**: потолок доли перепосылок, PLI не чаще ~1/с от участника |
| Разбор входа от враждебного участника | C++, фаззится Google | Rust, лимиты памяти, фаззинг `media` | ✅ + **P1**: фаззинг всего нового разбора |
| «Положить трубку» мимо очередей | уязвимость класса RingRTC CVE-2026-113380 | инвариант 12 | ✅ sans-IO это сохраняет |

## Сводка

**P1 — первая версия LiteRTC** («звонки не сыплются и не протекают»):

1. Формат v2: байт версии, случайный номер потока, сквозной номер пакета, настоящее время
   захвата у видео, поворот и fps в протоколе.
2. Обратная связь: SR, RR (потери, джиттер, RTT), отчёт о времени прихода, NACK, PLI.
3. Перепосылка (RTX) с ограниченной историей и потолком доли.
4. Пропуск до ключевого кадра и редкий периодический ключевой.
5. Оценка полосы (задержка + потери), pacer с приоритетами, команда битрейта кодеку.
6. Звук: использовать FEC Opus при декодировании; CBR или выравнивание размера; DTX выключен
   осознанно.
7. Статистика по участникам.
8. Симулятор сети и фаззинг.

**P2:** пробы полосы, распределение полосы, лестница разрешений, показ видео по меткам
времени и синхронизация губ в LiteRTC, уровень звука в заголовке, RED для звука,
растяжение времени, журнал звонка, обмен возможностями в сигнализации.

**P3:** FEC видео, временные слои SVC, playout-delay, Opus DRED и нейро-PLC, VP9/AV1,
своя обработка звука для десктопа, мягкий лимитер, ретранслятор + SFrame.

**Не берём:** ICE/STUN/TURN, DTLS/SRTP, SDP/JSEP, DataChannel, DTMF, REMB, XR/SDES.

## Что из этого меняет ADR-014

- Формат v2 получает **номер потока** и **сквозной номер пакета** (их не было).
- В «Восстановление» добавляется **починка FEC Opus** (сейчас избыточность платится зря).
- Новый пункт безопасности: **размер пакетов звука** (CBR/выравнивание) и осознанно
  выключенный DTX.
- Pacer — **с приоритетами** (звук впереди видео).
- Порядок: исправления звука (FEC, CBR) дешёвые и не зависят от переноса — их можно
  сделать сразу, до шагов 2–3.
