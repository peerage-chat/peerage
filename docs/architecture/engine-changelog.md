# Журнал изменений движка

Что меняется в Rust-части — `core`, `messenger`, `engine`, `androidjni`, `ygg` — и почему.
Здесь записан **контракт**: команды и JNI, события и DTO, схема базы, наблюдаемое поведение.
Внутренние рефакторинги без смены контракта сюда не пишутся: их видно в git.

## Правила

1. **Сначала причина.** Каждое изменение отвечает на пункт плана, ADR, находку ревью (R-NNN)
   или баг из журнала полировки. Если причина — «UI так удобнее», сначала проверить, что
   логика действительно принадлежит движку ([ADR-003](../adr/ADR-003-engine-api.md)), а не
   клиенту.
2. **Запись — в том же коммите**, что и изменение. Коммит движка без записи здесь —
   незаконченный.
3. **Схема базы.** Новая колонка или таблица — с миграцией на старой базе (ALTER/перенос), и в
   записи это отмечено. До раздачи беты формат ломать можно, но запись обязательна и тогда.
4. **Контракт.** Новая или изменённая команда, событие, поле DTO, JNI — перечислены по именам.
   Старое удалено — тоже.
5. **Поведение.** Изменилось, что видит пользователь или собеседник (что уходит в сеть, что
   хранится), — одной строкой, без пересказа кода.
6. **Проверка.** Какой тест закрепляет новое поведение.

Формат записи — новые сверху:

```
## ГГГГ-ММ-ДД · коротко · коммит
Причина: …
Контракт: …   Схема: …   Поведение: …   Совместимость: …   Тесты: …
```

## 2026-11-02 · Звонки в ленте личного чата · 82769ee (UI 2.8б)

**Причина:** app-ui.md → «Чат», макет `special/Calls`; план, шаг 2.8. Звонки жили только в
журнале «Звонки» — в переписке их не было видно. Склеивать журнал с лентой в клиенте нельзя
честно: лента приходит страницами по строкам базы, журнал — отдельным списком.

**Модель.** Личный звонок — строка переписки, которую движок ведёт сам по ходу звонка.
Журнал звонков остаётся источником (исход, длительность); строка ленты — его отражение в
чате с этим человеком. Звонки в комнате группы в ленту не попадают.

| Поле строки | Значение |
|---|---|
| `kind` | `call` или `video_call` |
| `id` | id записи журнала звонков (локальный) |
| `sender`, `mine` | кто звонил: входящий — собеседник, исходящий — я |
| `text` | исход: `answered` · `missed` · `declined` · `unanswered` |
| `duration_ms` | длительность разговора (0 — не было) |
| `time` | начало звонка |

- **Схема:** `calls.video INTEGER NOT NULL DEFAULT 0` (в `CREATE` и `ALTER` для старых баз);
  строки ленты — обычные `chat_messages`, без новых колонок.
- **Хранилище:** `CallRecord.video`; `CallStore::start(…, video, …)`, `CallStore::get(id)`;
  `MessageStore::upsert_call(chat, msg) -> row` — вставить или обновить исход и длительность.
  Поиск по переписке строки звонков не находит.
- **Поведение:** каждое изменение записи журнала (начало, ответ, отказ, конец) обновляет
  строку ленты и шлёт событие `message` с ней — клиент заменяет строку на месте.
- **Контракт:** `CallEntry.video` в журнале звонков; в истории личного чата появляются строки
  `kind = call | video_call`. Копия данных: `video` в записи звонка (старые копии — без
  видео).
- **Исправление попутно:** входящий звонок считался отвеченным, как только в комнате
  появлялся звонивший (его присутствие приходит раньше, чем ответ). Отметка «отвечен» по
  присутствию — теперь только у исходящего: входящий отвечается кнопкой (`answer_call`).
- **Совместимость:** по сети ничего не меняется. Звонки до этой правки в ленту задним числом
  не попадают.
- **Тесты:** `room_ring::dm_calls_show_up_in_the_chat_feed` — видеозвонок: у звонившего
  строка «без ответа», у второго «пропущен»; после входа второго — «отвечен» у обоих, после
  выхода — с длительностью; строка одна на звонок; поиск её не находит.

## 2026-11-02 · Системные строки группы: что произошло и с кем · 09421aa (UI 2.8а)

**Причина:** app-ui.md → «Чат группы», «Системные строки» (пять видов, без рода), макет
`special/GroupSystem`; план, шаг 2.8. Раньше строка знала только «у кого-то сменился состав»:
`system = true`, автор — тот, кто сделал коммит, без вида события и без того, кого оно касается.

**Модель.** Системная строка — событие группы: **вид** (`kind`), **о ком** (`sender`) и
**параметр** (`text`). Текст строки собирает клиент из вида — движок слов не хранит.

| `kind` | `sender` (о ком) | `text` (параметр) | Строка у клиента |
|---|---|---|---|
| `created` | создатель | — | «Группа создана · Борис» |
| `joined` | вступивший | ключ пригласившего (hex) | «Кирилл в группе · приглашение: Борис» |
| `left` | вышедший или удалённый | — | «Мария больше не в группе» |
| `renamed` | кто переименовал | новое название | «Новое название: «Дача 2026»» |
| `admin` | новый администратор | — | «Кирилл — теперь администратор» |

Строки `system` старого вида (`kind = "text"`, пустой текст) остаются как были: «изменение
состава». `renamed` и `admin` — контракт и отрисовка сейчас, источники — с командами
переименования и передачи прав (план 3.5); до тех пор движок их не пишет.

- **MLS (`group`):** `Incoming::MembershipChanged { actor, added, removed }` — кого коммит
  добавил и кого убрал (ключи из credential; убранные — до слияния коммита). Один и тот же
  ключ в обоих списках (перевыпуск) взаимно сокращается; коммит, где после этого пусто, —
  `Rekeyed`. `Member::swap` — убрать и добавить одним коммитом (`swap_members`).
- **`groupchat`:** `Inbound::Membership { actor, added, removed }`;
  `GroupChat::readd_member(peer, key_package)` — перевыпуск одним коммитом.
- **Источники в `GroupManager`:** `create` → `created` (я); добавление по KeyPackage →
  `joined` (он, пригласил я); вступление по Welcome → `joined` (я, пригласил приславший
  Welcome); `remove_member` (и выход по просьбе) → `left`; входящий коммит → `joined`
  на каждого добавленного (пригласил автор коммита) и `left` на каждого убранного.
- **Поведение:** перевыпуск отставшего (resync, ADR-004) — теперь ОДИН коммит Remove+Add
  вместо двух: остальные не видят «вышел/вошёл», а эпоха двигается один раз.
- **Схема:** без изменений — вид в `kind`, параметр в `text`.
- **Совместимость:** по сети ничего не меняется (коммиты MLS те же; swap — обычный коммит с
  двумя предложениями). Старые строки читаются как раньше.
- **Тесты:** `group` — swap у третьего участника — `Rekeyed`, добавление/удаление — со
  списками; `group_flow` — строки у админа и у вступившего, удаление и выход, resync без строк.

## 2026-11-02 · Реакции входят в копию данных · (UI 2.7, доделка)

**Причина:** при записи реакций (ниже) копия данных их не включала — восстановленная переписка
приходила без реакций (журнал полировки, 2026-11-02).

- **Формат копии:** новая запись `{"rec": "reactions", "items": [{chat, scope, msg_id,
  msg_sender, who, emoji, at}]}` — по тому же выбору, что переписка (личные / заметки /
  группы), со снятыми (пустой `emoji`). Версия манифеста та же (1).
- **Хранилище:** `MessageStore::export_reactions() -> Vec<ReactionRow>` — все строки как есть.
- **Поведение импорта:** слияние через `react` (последнее слово по `at`), эмодзи проверяется
  `reaction_ok`; заметки переадресуются на текущее «я», как сами сообщения. Повторный импорт
  ничего не задваивает.
- **Совместимость:** копии без записи читаются как раньше. Клиент до этой правки новую копию
  не прочтёт (незнакомая запись — ошибка разбора); до раздачи беты допустимо.
- **Тесты:** `backup::reactions_ride_along_with_their_chat` (engine).

## 2026-11-02 · Реакции на сообщения · 29e23fa (UI 2.7)

**Причина:** app-ui.md → «Реакции» (шаг 7f), макеты `chatact/ActMenu`, `chatact/Reactions`,
`chatact/ReactWho`; план, шаг 2.7. Реакций в движке не было вовсе.

**Модель.** У человека на сообщение — одна реакция: повтор снимает, другая заменяет (решает
клиент, движок хранит последнее слово). Реакция — пара «сообщение (автор + id, ADR-006) +
кто» → эмодзи. Порядок изменений одного человека — по его времени `at` (мс): позднее побеждает,
опоздавший пакет старое не возвращает. Снятие — пустой эмодзи с тем же `at` (надгробие в
таблице), иначе опоздавшая постановка воскресила бы снятую реакцию.

- **Протокол (личный чат):** `Payload::React { id, target, target_mine, emoji, at }` — надёжно
  (retry-until-Ack, офлайн-очередь), бакет CONTROL; `target_mine` — с точки зрения
  отправителя, переворачивается на приёме, как у закрепа. Старые клиенты незнакомый тип
  пропускают.
- **Протокол (группа):** `AppMsg::React { target, sender, emoji, at }` (`"t": "react"`), кто —
  из MLS, не из тела. Реагировать может любой участник.
- **Проверка:** эмодзи — 1..=64 байт (`MAX_REACTION`), без управляющих символов и пробелов
  (`protocol::reaction_ok`), на отправке и на приёме.
- **Схема:** таблица `reactions (chat, scope, msg_id, msg_sender, who, emoji, at)`, ключ — до
  `who`. Создаётся `CREATE IF NOT EXISTS`, миграция не нужна. Отзыв (`retract_many`),
  удаление у себя и очистка чата стирают и реакции. В копию данных — см. запись выше.
- **Хранилище:** `MessageStore::react(chat, msg_id, msg_sender, who, emoji, at) -> bool`
  (изменилось ли), `reactions(chat, msg_id, msg_sender)`; `StoredMessage.reactions` —
  только на чтение, заполняет `history`: `[{emoji, who: [hex…]}]`, эмодзи по первому
  появлению.
- **Контракт:** `Engine::react(chat, id, sender, emoji) -> bool` (пустой эмодзи — снять);
  `GroupCmd::React`; JNI `Native.react(session, chat, isGroup, id, sender, emoji): Boolean`;
  событие `UiEvent::Reactions { chat, group, id, sender, reactions }` — новый набор на одно
  сообщение, клиент правит его на месте.
- **Тесты:** хранилище (порядок по `at`, снятие, стирание при отзыве), личный чат (доходит,
  заменяется, снимается), группа (доходит до участника, автор из MLS).

## 2026-11-02 · Отзыв «у всех» оставляет строку «Сообщение удалено» · e718449 (UI 2.5)

**Причина:** app-ui.md → «Удалённое «у всех» оставляет строку», макет `special/Deleted`
(план, шаг 2.5). Раньше отозванное исчезало бесследно, и собеседник не видел, что что-то было.

- **Схема:** без изменений. Надгробие — обычная строка `chat_messages` с `kind = 'deleted'`.
- **Хранилище:** `MessageStore::retract_many(chat, refs)` — строка остаётся на месте (время,
  автор), содержимое стирается (текст, вложение, миниатюра, цитата, пересылка, упоминания),
  закреп снимается. `edit_text` надгробие не правит.
- **Поведение:** `Engine::retract_messages` (своё) и приём `Retract` (чужое) в личном чате,
  `GroupManager::retract` и приём отзыва в группе — теперь делают надгробие вместо `DELETE`.
  Побочно: досылка того же id после отзыва больше не воскрешает сообщение (строка есть →
  `append` отвечает `Duplicate`); правка, догнавшая отзыв, текст не возвращает.
- **Контракт:** событие `Retracted { peer, id }` и `GroupRetracted { gid }` — те же; смысл
  «строка стала надгробием». В истории у сообщения может быть `kind: "deleted"`.
- **Совместимость:** по сети ничего не меняется. Старые клиенты отозванное стирали — у них
  строки нет.
- **Тесты:** `store::retract_leaves_a_tombstone` (core),
  `retract_leaves_a_deleted_row_on_both_sides` (msg_actions), `group_reply_and_retract`
  (group_flow, проверка надгробия у обоих).

## 2026-11-02 · «Не доставлено» и «Повторить» · 688a8e1 (UI 2.4)

**Причина:** движок никогда не выдавал статус `failed`: сброшенное из очереди отправки (или
выброшенное по сроку незнакомцу/заблокированному) стиралось, а пузырь оставался «в очереди».
App-ui.md → «Статусы своих».

- **Схема:** `outbox.failed INTEGER NOT NULL DEFAULT 0` (в `CREATE` и `ALTER` для старых баз).
- **Хранилище:** записи с `failed = 1` не досылаются и не считаются ждущими;
  `OutboxStore::mark_failed`, `OutboxStore::retry(peer, msg_id, now)`. Менеджер: `waiting`,
  `fail`, `remove`, `retry`, `expired` (заменили `clear_all` и `prune_expired`).
- **Поведение:** сброс очереди и срок досылки — своё сообщение переписки получает статус
  `failed` (запись остаётся для повтора), служебный пакет стирается. «Повторить» возвращает
  запись в очередь с тем же `msg_id` — получатель дедуплицирует.
- **Контракт:** `Engine::retry_message(key, id) -> bool`; JNI `Native.retryMessage(session, key,
  id): Boolean`; событие `UiEvent::Failed { peer, id }` (`"failed"`). Мессенджер:
  `hold(peer, id)` / `resume(peer)`.
- **Совместимость:** по сети ничего не меняется.
- **Тесты:** `outbox::failed_rows_leave_the_queue_until_retried` (core),
  `cleared_message_fails_then_retry_delivers` (outbox_flow).

## 2026-11-02 · Проверка копии ключа словами · 8aa5567 (UI 1.6)

**Причина:** напоминания о копии ключа — копия считается сделанной только после проверки слов.

  не выходит — наружу только «да/нет».

## 2026-11-02 · Число узлов — только поднятые; приглашения после старта · 07a5f69

**Причина:** без сети шапка показывала «8 узлов», статус «нет соединения» не появлялся;
сохранённые приглашения в группы не появлялись после перезапуска.

- **Поведение:** `ygg_peer_count` считает только пиров с `Up = true`. На старте движок
  объявляет `GroupInvitesChanged` вместе с остальными списками.
- **Тесты:** `ui_events` (приглашения после старта).
