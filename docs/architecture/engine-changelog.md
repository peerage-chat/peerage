# Журнал изменений движка

Что меняется в Rust-части — `core`, `messenger`, `engine`, `androidjni`, `ygg` — и почему.
Здесь записан **контракт**: команды и JNI, события и DTO, схема базы, наблюдаемое поведение.
Внутренние рефакторинги без смены контракта сюда не пишутся: их видно в git.

## Правила

1. **Сначала причина.** Каждое изменение отвечает на пункт плана, ADR, находку ревью (R-NNN)
   или баг из журнала полировки. Если причина — «UI так удобнее», сначала проверить, что
   логика действительно принадлежит движку ([ADR-003](../adr/ADR-003-engine-api.md)), а не
   клиенту.
2. **Запись — в том же коммите**, что и изменение. Коммит движка без записи здесь —
   незаконченный.
3. **Схема базы.** Новая колонка или таблица — с миграцией на старой базе (ALTER/перенос), и в
   записи это отмечено. До раздачи беты формат ломать можно, но запись обязательна и тогда.
4. **Контракт.** Новая или изменённая команда, событие, поле DTO, JNI — перечислены по именам.
   Старое удалено — тоже.
5. **Поведение.** Изменилось, что видит пользователь или собеседник (что уходит в сеть, что
   хранится), — одной строкой, без пересказа кода.
6. **Проверка.** Какой тест закрепляет новое поведение.

Формат записи — новые сверху:

```
## ГГГГ-ММ-ДД · коротко · коммит
Причина: …
Контракт: …   Схема: …   Поведение: …   Совместимость: …   Тесты: …
```

## 2026-11-25 · Принятый звонок не становится отклонённым · (этот коммит)

**Причина:** п. 56 плана беты (с телефона): принятый звонок, из которого первым вышел
звонивший, в журнале — «отклонён».

- **Поведение:** `room_decline_dm` помечает входящий отклонённым, только пока он не принят.
  Клиент шлёт отмену и при выходе из разговора, где собеседника уже нет (для него это
  неотличимо от недозвона); раньше это перезаписывало «answered» на «declined» и обнуляло
  длительность. Теперь запись остаётся отвеченной, длительность ставит `room_leave`.
- **Контракт, схема:** без изменений. **Совместимость:** только локальный журнал.
- **Тесты:** `room_ring::answered_call_left_by_caller_stays_answered`.

## 2026-11-24 · «По чатам» в хранилище — по файлам, а не по сообщениям · c335c84c

**Причина:** находка при проверке п. 27 на эмуляторе: чат «весил» 83 kB при 65 kB всего на
устройстве. `storage_stats.chats` складывал размер на каждое сообщение со вложением, а одно
фото, отправленное несколько раз, — один файл (между чатами повтор уже исключался, внутри —
нет).

- **Контракт:** без изменений (те же поля `files`, `bytes`).
- **Поведение:** в чате каждый блоб считается один раз; сумма по чатам больше не превышает
  объём на диске, кроме файлов, общих для нескольких чатов (их место — в каждом из них).
- **Схема:** без изменений.  **Совместимость:** локальный API.
- **Тесты:** `blob_gate::storage_by_chat_counts_a_file_once`.

## 2026-11-24 · Очистка вложений по чатам и типам · 998f02b2

**Причина:** пункт 27 списка с телефона (beta.md): «Очистить вложения» удаляло всё разом, а
место обычно съедает один чат или один тип (видео).

- **Контракт:** `ClearFilter { chats, kinds }` (+ `ClearFilter::from_json`: битый чат или
  незнакомый тип — `None`, а не пропуск, иначе очистка молча расширилась бы),
  `Engine::clear_blobs_where(&ClearFilter) -> u64`, `Engine::clear_preview(&ClearFilter) -> u64`,
  `attachment_kind(kind)` — вид для «Хранилища» (`image|video|voice`, остальное — `file`).
  `clear_blobs()` = пустой фильтр. JNI: `Native.clearBlobs` заменён на
  `clearBlobsWhere(ptr, json)` и `clearBlobsPreview(ptr, json)`, JSON
  `{chats: [{chat, group}], kinds: [...]}`.
- **Поведение:** под фильтр попадает блоб, на который ссылаются вложения из выбранных чатов и
  типов, — кроме тех, на которые ссылается и что-то вне фильтра (файл один на все чаты); лица и
  миниатюры — никогда. Пометка «скачано» снимается ровно с удалённого. Докачки бросаются только
  при полной очистке. `storage_stats.by_kind` теперь в тех же четырёх видах, что и фильтр
  (раньше — сырой `kind` вложения): клиент чистит ровно те группы, что видит.
- **Схема:** без изменений.  **Совместимость:** локальный API; провод не тронут.
- **Тесты:** `blob_gate::clear_by_chat_and_kind_keeps_what_others_still_show` (картинки чата B
  уходят, общая с C и файл B остаются, предпросмотр = освобождённое; тип во всех чатах; пустой
  фильтр — всё), `blob_gate::clear_filter_from_json_rejects_what_it_cannot_read`.

## 2026-11-24 · Убран агрегат присутствия группы · ecd2799e

**Причина:** пункт 26 списка с телефона (beta.md): в составе группы были только «в сети» и «не в
сети», а «на связи» — нет; и шапка группы считала «в сети» по-своему. Строку «N уч · M в сети»
считал движок (`group_presence`: ростер ∩ «пир отвечает»), то есть «на связи» шло в «в сети».
Присутствие человека в клиенте — одно (`AppModel.presence`: «в сети» / «на связи» / «не в
сети»), и группа теперь считается из него же, по составу (`groupMemberKeys`).

- **Контракт:** удалены `Engine::group_presence`, `net::GroupPresence` и JNI
  `Native.groupPresence`. Замены в движке нет — клиент считает по составу и присутствию.
- **Схема:** без изменений.  **Поведение:** в сеть ничего нового не уходит.
- **Совместимость:** только локальный API; формат на проводе не тронут.
- **Тесты:** ушли `group_presence_self_only`, `group_presence_counts_self_as_online` (вместе
  с функцией); `cargo check -p peerage-engine -p peerage-android --tests`.

## 2026-11-24 · Докачка блоба уступает переписке: окно по задержке · f2ea165f

**Причина:** пункт 10 списка с телефона (beta.md): пока качается большое вложение, сообщения
в обе стороны встают. Движок вложение не блокирует (отправка — свой поток, приём — по чанку),
но окно докачки было фиксированным — 64 чанка ≈ 770 КБ в полёте. На медленном меше это
секунды очереди в канале, и текст, Ack и keepalive ждут за чанками.

- **Контракт:** без изменений.
- **Поведение:** окно докачки ведётся по задержке, как у фоновых передач LEDBAT/uTP
  (`engine/src/blob_window.rs`): база — минимум RTT чанка за последние 1–2 мин; своя очередь
  меньше 100 мс — окно растёт (до прежних 64), больше — сжимается (до 2), таймаут чанка —
  вдвое. Начальное окно — 16 чанков. RTT берётся только у чанка, спрошенного один раз.
- **Совместимость:** только у получателя; отдающий не менялся.
- **Тесты:** `blob_window::tests` (пустой канал → 64, своя очередь → 2, очередь в цель —
  окно на месте, потеря — вдвое раз за волну, смена маршрута забывает старую базу);
  `download_asks_one_window_at_a_time` — начальное окно 16. На медленном канале не
  проверено: эмуляторы и loopback очереди не создают — проверка на телефоне.

## 2026-11-24 · Два статуса: «на связи» и «в сети» · 7dc126e9

**Причина:** пункт 9 списка с телефона (beta.md): «в сети» загоралось, пока приложение просто
работало в фоне. Нужно отдельно «приложение открыто», и чтобы его можно было скрыть.

- **Контракт:** `Payload::Ping`/`Pong` — новое поле `active: bool` (приложение открыто).
  `messenger::Event::Presence { peer, online, active }`, `Messenger::set_active(bool)`.
  `UiEvent::Presence` — поле `active`. `Engine::set_app_foreground(bool)`,
  `Engine::set_in_app_status(bool)`; `privacy.json` и `privacy_json()` — поле `in_app`
  (нет в файле — true). JNI: `Native.setAppForeground`, `Native.setInAppStatus`.
- **Поведение:** открыл приложение (и не скрыл) — своим (набор `targets`) сразу уходит Ping с
  `active`, убрал — Ping без него; в Pong — то же; вернувшемуся своему, пока мы «в сети», — Ping
  сразу, а не через keepalive. Чужим флаг не уходит и от чужих не читается. Движок показывает
  `active` только у контакта и только если своё не скрыто (взаимно). С уходом связи `active`
  сбрасывается.
- **Совместимость:** `active: false` не сериализуется — пинг без флага те же байты, что раньше;
  старый клиент поле пропускает и видит только «на связи». Пакет остаётся в бакете CONTROL.
- **Тесты:** `protocol::active_flag_is_compatible_with_old_ping`, бакет — в
  `presence_with_transit_claim_stays_in_control_bucket`; messenger
  `active_flag_reaches_contacts_only`, `active_flag_is_told_on_reconnect`; engine
  `in_app_status_is_shown_by_default_and_mutual`; форма события — `event_wire_shape_is_stable`.

## 2026-11-24 · Зачистка JPEG оставляет поворот кадра · b6404667

**Причина:** пункт 2 списка с телефона (beta.md) — вложения в ленте по своим пропорциям. При
проверке выяснилось: снимок с камеры, у которой пиксели лежат боком, а положение записано
тегом EXIF Orientation, уходил лёжа — `blob::scrub` выбрасывал APP1 целиком вместе с тегом.

- **Контракт:** без изменений (`blob::scrub(mime, data)`).
- **Поведение:** из APP1 (EXIF) берётся только тег 0x0112 (SHORT, 1..8) из IFD0; если он не 1,
  на место исходного сегмента встаёт новый APP1 из одной записи (36 байт, big-endian TIFF).
  Всё остальное — модель, дата, GPS, миниатюра, XMP — уходит, как раньше. Поворот — не
  приватные данные: он виден и по самой картинке.
- **Совместимость:** формат вложения не меняется; старый клиент тег не читает и показывает
  снимок, как раньше (лёжа).
- **Тесты:** `scrub::tests::jpeg_keeps_only_orientation_from_exif` (до правки падал: тег
  терялся), прежние тесты JPEG и фаззер `garbage_never_panics`.

## 2026-11-24 · Зачистка метаданных GIF · 642f4460

**Причина:** баг беты — GIF с системной клавиатуры не вставлялся в поле сообщения. Вставка
делается в клиенте, но GIF до сих пор уходил как есть: `blob::scrub` его не узнавал, а
комментарии и XMP (расширение приложения) в GIF — тот же приватный слой, что EXIF у JPEG.

- **Контракт:** без изменений (`blob::scrub(mime, data)`).
- **Поведение:** GIF87a/89a разбирается по блокам. Уходят комментарии (0xFE), расширения
  приложений, кроме петли анимации (NETSCAPE2.0 / ANIMEXTS1.0, — так в GIF лежит XMP), и всё
  после трейлера. Остаются кадры, управление кадром (0xF9) и текстовый слой (0x01, это
  изображение) — байт в байт. На обрыве остаток отдаётся как есть, как у PNG и JPEG.
- **Совместимость:** формат вложения не меняется; получатель видит тот же GIF без метаданных.
- **Тесты:** `scrub::tests::gif_strips_comment_and_xmp_keeps_animation` (до правки падал: GIF
  проходил нетронутым), фаззер `garbage_never_panics` — с заголовком GIF.

## 2026-11-23 · Запрос в контакты несёт адрес отправителя · 11ef63d (до раздачи беты)

**Причина:** баг с живого меша. Запрос в контакты не доходил: на эмуляторах он висел
«отправлен» больше часа, хотя оба узла были в сети. Регрессия шага 8 (8.2: «ключ личности
адресом не бывает»). Незнакомец приходит с транспортного ключа, а анти-спуфинг на приёме
пускал пакет, только если адрес совпадает с личностью, связка уже известна или пакет —
объявление о смене адреса. Запрос не подходил ни под одно условие и молча отбрасывался.
Отвечать незнакомцу тоже было некуда: Ack и принятие уходили на ключ личности. Loopback-тесты
этого не ловили: узлы в них сидели на ключе личности, то есть в мире, которого после шага 8
нет.

- **Контракт:** `Payload::ContactRequest` — новые поля `record`, `sig` (подписанная запись
  адреса v2 отправителя, как в `TransportRotate`). `Messenger::send_contact_request(peer,
  greeting, name, address: &SignedRecord)`. `Event::ContactRequest` — поля `record`, `sig`.
  `GateStore::upsert_request(…, address: (&[u8], &[u8]))`, `ContactRequest.record` /
  `record_sig` (в JSON для UI не попадают). `engine::node_epoch(dir)` — эпоха, на ключе
  которой поднимается узел (её же берут тесты). `mesh_node`: `--request <код>`, строка
  `CODE`, логи движка в stderr (`PEERAGE_LOG`).
- **Поведение:** запрос, чья запись подписана личностью отправителя и указывает на адрес, с
  которого он пришёл, проходит анти-спуфинг сам. Мессенджер сразу запоминает связку
  «личность → адрес», и Ack уходит по адресу. Движок хранит запись с запросом: адрес
  незнакомца с запросом входит в карту адресов (после перезапуска тоже). При принятии запись
  становится адресом контакта, с той же проверкой подписи и эпохи, что у объявления о смене
  адреса. Отклонение и блок снимают связку. Адрес контакта связка из запроса не меняет.
- **Схема:** 2 — `contact_requests.record`, `contact_requests.record_sig` (BLOB, пусто по
  умолчанию), первый шаг `STEPS` после заморозки. У запроса из схемы 1 записи нет.
- **Совместимость:** запрос без записи не декодируется. Старых клиентов нет (до раздачи
  беты), но телефон и эмуляторы со старой сборкой — `pm clear`: очередь отправителя держит
  запрос прежнего вида.
- **Тесты:** `gate.rs`, `gate_rooms.rs`, `profile.rs` теперь поднимают узлы на
  транспортном ключе эпохи, как телефон (4 теста гейта падали до правки). Контакты
  заводятся по коду (`befriend`), а не голым ключом. Атакующий в `gate_rooms` тоже сидит на
  транспортном ключе. `db::migration::v1_request_survives_and_gets_empty_address`, запись
  адреса в `gate_request_keeps_first_and_survives_reopen`, размер запроса с записью в
  `contact_request_and_accept_hide_among_text`. Живой меш: `mesh_node --request <код>` →
  карточка и уведомление на эмуляторе, принятие вернулось узлу.

## 2026-11-23 · Узлы входа: свои адреса и тумблер узлов из сборки · b9c69d5 (до раздачи беты)

**Причина:** чеклист перед публикацией — список пиров Yggdrasil был зашит в сборку
(`peers/public-peers.txt`): там, где публичные узлы недоступны, связи не было вовсе, а

- **Контракт:** модуль `engine::peers` — `PeerConfig {builtin, own}`, `parse_uri`,

  `PeerSettings {builtin_on, builtin, own}`. `Engine::peer_settings`, `peers_add`,
  `peers_remove`, `peers_set_builtin`; `reconnect_peers` и подъём узла (старт, смена адреса)
  берут адреса из настройки, а не из сборки. JNI: `peerSettings`, `peersAdd`, `peersRemove`,
  `peersSetBuiltin`. `Transport::remove_peer` (по умолчанию no-op), `Messenger::remove_peer`,
  `peerage_ygg::Node::remove_peer`, `ygg_remove_peer` (libygg, `core.RemovePeer`).
  `PeerStat.uri` / `ygg_peers_json` поле `uri` — по нему клиент ставит статус узла.
- **Поведение / схема:** `peers.json` в каталоге профиля (атомарно); нет файла — узлы из
  сборки включены, своих нет. Адрес — `tls`/`tcp`/`quic`, хост, порт 1–65535 (запрос после
  порта допустим); повтор своего или из сборки — отказ. Правка применяется сразу, без
  перезапуска. В сеть ничего нового не уходит. **Совместимость:** новый файл, старые
  установки получают умолчание.
- **Тесты:** `peers::tests` (разбор адреса, повторы, тумблер, перезапуск),
  `tests/entry_nodes.rs` (что доходит до транспорта сразу и после перезапуска).

## 2026-11-23 · Без переходов для данных до заморозки · 616460e (бета 8, решение владельца)

**Причина:** до раздачи беты формат ломать можно, а переходы со старого состояния — то же
«два формата» (решение владельца 2026-11-23: телефон и эмуляторы — `pm clear`).

- **Контракт:** `upgrade_address` → `ensure_address(dir)` (адреса нет — эпоха «сейчас»);
  `TransportMeta` без поля `v`. `StoreError::ProfileVersion`.
- **Поведение / схема:** `profile.json` только v2 (`version`, `seed`, `kind`, `hidden` —
  обязательны); v1 — ошибка старта. Схема базы 1 — только `CREATE`: старые `ALTER`,
  перенос «без звука», сброс запросов 7i и прежнего индекса `messages_fts` убраны.

## 2026-11-02 · Системные строки группы: что произошло и с кем · 9c5905a (UI 2.8а)

**Причина:** app-ui.md → «Чат группы», «Системные строки» (пять видов, без рода), макет
`special/GroupSystem`; план, шаг 2.8. Раньше строка знала только «у кого-то сменился состав»:
`system = true`, автор — тот, кто сделал коммит, без вида события и без того, кого оно касается.

**Модель.** Системная строка — событие группы: **вид** (`kind`), **о ком** (`sender`) и
**параметр** (`text`). Текст строки собирает клиент из вида — движок слов не хранит.

| `kind` | `sender` (о ком) | `text` (параметр) | Строка у клиента |
|---|---|---|---|
| `created` | создатель | — | «Группа создана · Борис» |
| `joined` | вступивший | ключ пригласившего (hex) | «Кирилл в группе · приглашение: Борис» |
| `left` | вышедший или удалённый | — | «Мария больше не в группе» |
| `renamed` | кто переименовал | новое название | «Новое название: «Дача 2026»» |
| `admin` | новый администратор | — | «Кирилл — теперь администратор» |

Строки `system` старого вида (`kind = "text"`, пустой текст) остаются как были: «изменение
состава». `renamed` и `admin` — контракт и отрисовка сейчас, источники — с командами
переименования и передачи прав (план 3.5); до тех пор движок их не пишет.

- **MLS (`group`):** `Incoming::MembershipChanged { actor, added, removed }` — кого коммит
  добавил и кого убрал (ключи из credential; убранные — до слияния коммита). Один и тот же
  ключ в обоих списках (перевыпуск) взаимно сокращается; коммит, где после этого пусто, —
  `Rekeyed`. `Member::swap` — убрать и добавить одним коммитом (`swap_members`).
- **`groupchat`:** `Inbound::Membership { actor, added, removed }`;
  `GroupChat::readd_member(peer, key_package)` — перевыпуск одним коммитом.
- **Источники в `GroupManager`:** `create` → `created` (я); добавление по KeyPackage →
  `joined` (он, пригласил я); вступление по Welcome → `joined` (я, пригласил приславший
  Welcome); `remove_member` (и выход по просьбе) → `left`; входящий коммит → `joined`
  на каждого добавленного (пригласил автор коммита) и `left` на каждого убранного.
- **Поведение:** перевыпуск отставшего (resync, ADR-004) — теперь ОДИН коммит Remove+Add
  вместо двух: остальные не видят «вышел/вошёл», а эпоха двигается один раз.
- **Схема:** без изменений — вид в `kind`, параметр в `text`.
- **Совместимость:** по сети ничего не меняется (коммиты MLS те же; swap — обычный коммит с
  двумя предложениями). Старые строки читаются как раньше.
- **Тесты:** `group` — swap у третьего участника — `Rekeyed`, добавление/удаление — со
  списками; `group_flow` — строки у админа и у вступившего, удаление и выход, resync без строк.
