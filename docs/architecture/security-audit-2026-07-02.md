# Аудит безопасности крипто/MLS/транспорт — 2026-07-02

Разовый read-only аудит крипто-слоя перед вехами гранта NGI Zero. Область:
`core` (identity/crypto/protocol/media/vault/db/store), `group`/`groupchat` (MLS),
`messenger` (надёжность/каналы), `engine` (членство комнат), `ygg` (транспорт).
Ничего не менялось — только чтение и анализ.

**Отношение к [SECURITY.md](../SECURITY.md):** тот документ — канонический (основной
аудит ядра + скан зависимостей). Этот — **дополняющий** проход по крипто-свойствам
протокола после появления Android-поверхности. Где выводы расходятся со статусами
SECURITY.md — отмечено явно. Сводная модель — [threat-model.md](threat-model.md).

Итог: **примитивы применены корректно** (NaCl Box, XChaCha20, MLS через openmls —
без самопального крипто; nonce случайны; теги проверяются; анти-спуфинг на месте).
Memory-safety проблем и паник на FFI-границе в проверенных путях нет. Главный
реальный пробел — **нереализованные MLS Remove/Update** (заявленный PCS фактически
недостижим). Остальное — вопросы *расслоения гарантий*: слишком много свойств
держится на одном допущении о транспорте, которое стоит либо продублировать, либо
пере-верифицировать.

---

## HIGH

### H2 — MLS Remove/Update не реализованы → нет отзыва и нет PCS-восстановления
**Где:** `group/src/lib.rs` — есть `add`, `create_group`, `process`; **нет**
`remove_member` и нет self-`Update` (commit без смены состава для ротации ключа).
`groupchat`/`engine` их не вызывают (подтверждено grep по всему воркспейсу — ни
одного `remove_member`/`self_update`/`leave`).

MLS выбран ради Forward Secrecy и **Post-Compromise Security** (шапка
`group/src/lib.rs` это заявляет). Per-message FS в пределах эпохи работает. Но:
- **Отозвать участника нельзя.** Ушедший/скомпрометированный участник (A3)
  остаётся в группе навсегда.
- **PCS не восстанавливается по требованию.** Эпоха продвигается только при
  добавлении участника; Update-commit для ротации секрета эпохи не шлётся. Пока
  секрет эпохи утёк — атакующий читает групповой трафик до следующего add (который
  может не случиться никогда).

**Расхождение с SECURITY.md:** там PCS для групп числится свойством MLS. Свойство
поддержано *шифрсьютом*, но **операции, которые его реализуют, отсутствуют** — на
уровне протокола приложения PCS-восстановление и отзыв недостижимы. Это сильнейшая
из находок.

**Рекомендация:** реализовать `remove_member` (admin-секвенсор уже сериализует
изменения состава — риск одновременных commit низок) и периодический/ручной
self-Update. UI под системное событие «участник удалён» уже есть.

## MEDIUM

### M0 — forward secrecy для 1:1 держится ТОЛЬКО на транспортном ратчете
**Где:** `core/src/crypto.rs` (`shared_box`), `core/src/identity.rs`
(`x25519_secret`) — прикладной слой; ратчет — в зависимости ironwood (`iwe`), вне
нашего кода.

Прикладной 1:1-слой (NaCl Box) использует **статический** X25519-секрет из
долговременного seed: ключ Box для пары (A,B) неизменен весь срок жизни. Сам по
себе он FS/PCS **не даёт**. По [SECURITY.md](../SECURITY.md) (H2, «Закрыто») FS/PCS
для 1:1 обеспечивает ратчет-слой ironwood `iwe` поверх меша — и на трафик,
перехваченный наблюдателем на пути (A1), это распространяется: он видит выход
транспортного ратчета, а не голый Box-шифртекст.

**Почему всё же Medium, а не «закрыто»:**
1. **Единая точка отказа.** ВСЯ forward secrecy для DM = свойство одной внешней
   зависимости. Прикладной слой не добавляет ни бита FS (в отличие, скажем, от
   Signal, где FS в самом приложении). Тот же класс, что M3 (медиа).
2. **Не пере-верифицировано в этом проходе.** `iwe`-ратчет живёт в
   yggdrasil-go/ironwood (pin `v0.0.0-20260117…`), а не в нашем `transport`/`ygg`.
   Grep по нашему коду `iwe`/`ratchet` — пусто (шифрование внутри `core.WriteTo`).
   SECURITY.md отмечает «проверено по исходникам», но при обновлении ironwood
   свойство надо перепроверять — иначе тихий регресс обнулит FS всех DM.

**Рекомендация:** (а) закрепить конкретную проверенную версию ironwood и
пере-верифицировать `iwe`-ратчет при каждом апгрейде (тест/чек-лист); (б)
рассмотреть перевод 1:1 на MLS (группа из двух) — даст FS/PCS в самом приложении и
уберёт единоточечную зависимость. Совпадает с дорожной картой H1 в threat-model.

### M2 — доступ к медиа группового звонка не привязан к MLS-ростеру
**Где:** `engine/src/lib.rs` (`Event::RoomPresence` → `rs.remote.insert(peer,…)`,
`live_participants` → `sync_room_members`), гейт микса `engine/src/room_call.rs:166`.

Членство в звонке определяется **маячками присутствия по `gid`**: любой пир,
приславший валидный `RoomPresence` для известного `gid`, попадает в `members`, и
его аудио/видео проходит гейт микса (строка 166) и подмешивается; он же получает
медиа других. MLS-ростер группы при этом **не** проверяется.

Для **DM-звонков** не эксплуатируется: `room_id = hash(min(keyA,keyB) ‖ max(…))`
выводится только двумя сторонами. Для **групповых** — `gid` это MLS group_id,
известный всем участникам (и любому, кто его когда-либо видел, включая
неотзываемого ex-участника из H2). Такой актор входит в медиа звонка незваным:
слушает и инъектирует A/V.

**Расхождение/уточнение SECURITY.md:** раздел «Комнаты-звонки (H1)» уже отмечает
спуфинг presence-флагов «любым участником MLS-группы». Здесь острее: проблема не в
подмене флагов, а в том, что в состав звонка попадает пир, **не сверенный с
ростером** (в т.ч. не-участник/ex-участник, знающий `gid`). Гейт на приёме
(`room_call.rs:166`) корректен — дефект в наполнении `members`.

**Рекомендация:** для группового `gid` принимать в `members` только пиров из
текущего MLS-ростера (`groups.members(&gid)`). DM-путь оставить как есть. Частично
адресует и заявленную SECURITY.md авторизацию входа (H6).

### M3 — конфиденциальность/аутентичность медиа целиком на транспорте
**Где:** `core/src/media.rs` (шапка), `messenger/src/lib.rs` (ветка `CHAN_MEDIA` в
`receive_loop` — без `decode`/крипто), `messenger/src/lib.rs::send_media`.

Медиа-кадры (`CHAN_MEDIA`) идут **без прикладного шифрования и аутентификации** —
сознательно, ради оверхеда. Всё держится на корневом допущении (транспорт Ironwood
шифрует и аутентифицирует src). Задокументировано, но хрупко: регресс транспорта
или его замена молча раскрывают/разрешают спуфинг аудио/видео. Тот же класс, что
M0.

**Рекомендация:** закрепить явным инвариантом (частично в `invariants.md`) + тест/
ассерт, что медиа-путь не активируется на транспорте без e2e. Долгосрочно — лёгкий
SRTP-подобный слой ключом из MLS/Box (defense-in-depth).

### M4 — переиспользование одного ключа между протоколами (нет доменного разделения)
**Где:** `group/src/lib.rs::signer_from` (`SignatureKeyPair::from_raw(ED25519,
identity.seed(), pubkey)`); тот же seed → Yggdrasil-сертификат (`ygg_start`) и →
X25519 Box (`identity.x25519_secret`).

Один ed25519-seed подписывает: транспортный сертификат Ironwood, MLS-хендшейки
(credential + leaf signature) и служит основой X25519-ключа Box. Подпись из одного
контекста потенциально валидна в другом — классический cross-protocol риск. Прямого
эксплойта не найдено, но это анти-паттерн, сужающий эволюцию протоколов.

**Рекомендация:** доменное разделение — под-ключи из seed через KDF с контекстными
метками (HKDF info="mls-sig"/"transport"/"box"); MLS-ключ подписи отделить от
идентичности.

## LOW / by-design

### L1 — анти-replay кольцо ограничено; часть control-сообщений без дедупликации
`messenger/src/lib.rs::receive_loop` (`seen`/`SEEN_CAP = 4096`). Дедуп по хэшу байт,
кольцо на 4096 — повтор после вытеснения пройдёт. `Text` дедуплицируется PK БД,
`Ack` защищён `pending.peer == src`. Но `RoomInvite`/`RoomPresence`/`Ping`/
`RoomDecline` без `id`/дедупа — их повтор может повторно дёрнуть UI звонка / всплеск
присутствия. Импакт низкий (транспорт аутентичен; эффект — назойливость).
**Рекомендация:** freshness-окно по `Envelope.time` (см. L2) или счётчик на control.
Некритично для v1.0. (SECURITY.md M3 «Исправлено» — про механизм кольца; здесь —
про его границы и покрытие.)

### L2 — `Envelope.time` не аутентифицирован и не используется
`core/src/protocol.rs`: `time` вне запечатанного Box, в AEAD-AAD не входит, `decode`
игнорирует. Мёртвое малли­абельное поле; прямого вреда нет (транспорт аутентичен).
**Рекомендация:** либо занести `time` внутрь шифруемого `Payload` и проверять окно
свежести (закроет часть L1), либо убрать из конверта.

### L3 — тихий откат в plaintext при недоступности vault (десктоп)
`core/src/vault.rs::seal` (ветка `None` пишет маркер 0 = открытый текст). Если
`vault::init` не удался (headless-Linux без Secret Service), секреты (seed, история)
**молча** пишутся открытым текстом. На Android не воспроизводится (ключ из Keystore
через `init_with_key`), но десктоп-путь рискован.
**Рекомендация:** без инициализированного vault — предупреждать/отказывать записи
секретов, не писать plaintext молча.

### L4 — `wipe_user_data` при рассинхроне vault — footgun/локальный DoS
`engine/src/lib.rs::start` (ветка `VaultError::Decrypt` → `wipe_user_data`). При
несовпадении ключа движок **стирает** данные и генерирует новую идентичность.
Сценарий «переустановка поверх старых данных» это оправдывает, но повреждение
ключа/профиля ведёт к необратимой потере идентичности при следующем старте.
**Рекомендация:** перед wipe — бэкап каталога в `*.corrupt` + явное уведомление UI.

## Что проверено и НАРЕКАНИЙ НЕТ

- **NaCl Box:** случайный 192-битный nonce на сообщение, префикс `nonce‖ct`, тег
  Poly1305 проверяется, чужой получатель/подделка → ошибка (тесты покрывают).
- **Анти-спуфинг надёжного канала:** `from == src` обязателен; `Ack` снимает
  pending только от адресата — корректно.
- **MLS add:** KeyPackage привязан к аутентифицированной идентичности пира
  (`identity == expected && sig_key == expected`) — подмена вступающего закрыта
  (= SECURITY.md H1 «Исправлено», подтверждаю).
- **`save_group` после мутаций:** отправка/приём/commit персистят состояние
  (инвариант соблюдён; коммент про sending-ratchet в `groups.rs` точен).
- **Гейт членства на приёме медиа:** `room_call.rs:166` отбрасывает медиа не от
  участника (проблема M2 — в *составе* `members`, не в самом гейте).
- **Ingress rate-limit:** per-src token-bucket ДО расшифровки, раздельно chat/media,
  eviction простаивающих бакетов — разумная анти-flood защита.
- **At-rest на Android:** SQLCipher включён (`androidjni` feature `sqlcipher`), ключ
  из Android Keystore; БД контактов/сообщений зашифрована.
- **Память/паники:** новых `unwrap()` на fallible-границах и паник на FFI в
  проверенных путях не замечено; JNI обёрнут `jni_safe!`.

4. **M4** — доменное разделение ключей.
5. **M3/L1–L4** — инварианты и мелкая жёсткость.
