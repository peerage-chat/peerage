# План 1 — медиа-движок до уровня WebRTC

Цель: реалтайм-медиа, устойчивое на реальных сетях (потери, джиттер, плавающая
полоса), с A/V-синхронизацией и нормальным UX звонка. Сейчас мы — «наивный
медиатранспорт без адаптации/восстановления»: фиксированный битрейт, нет
обратной связи, примитивный jitter-buffer, нет sync. Это и упирается в статтер.

## Стратегическая развилка: build vs adopt libwebrtc

Прежде чем пилить — зафиксировать решение. Два пути:
- **A. Дописать своё** поверх нашего транспорта (Yggdrasil). Полный контроль,
  serverless остаётся, но мы переизобретаем половину WebRTC (congestion control,
  FEC/NACK, jitter, AEC). Месяцы работы, высок риск тонких багов.
- **B. Взять медиа-движок libwebrtc** (его congestion control + jitter + APM +
  кодеки), но **выкинуть его ICE/DTLS** и гонять RTP-пакеты поверх Yggdrasil.
  Боевая, вылизанная годами база; цена — тяжёлая C++-зависимость и нетривиальная
  интеграция своего транспорта в чужой пайплайн.

Рекомендация: **гибрид.** Своё для того, что у нас уже работает и просто (захват,
кодеки MediaCodec/Opus, фрагментация), но **позаимствовать алгоритмы/идеи**
libwebrtc для адаптации и восстановления (M3/M4), а для аудио-обработки (M6) —
прямо взять готовое (APM или Android AudioEffect). Финальное решение — ADR.

## Фазы (по влиянию и зависимостям)

### M1 — Устойчивость приёмника: нормальный jitter-buffer (СРАЗУ)
Текущий пейсинг через `renderBaseNs`-offset упёрся в глубину пайплайна кодека
(~8 кадров): буфер 333мс снизил ресинки 4.3→1.9/сек, но не убрал. Нужен
**буфер-очередь пакетов на уровне приложения**, не привязанный к буферам кодека:
- ArrayDeque входящих access-unit'ов; prebuffer N кадров до старта выдачи;
  ровная выдача в декодер по часам.
- **Адаптивная глубина:** расти при underrun (рост джиттера), ужиматься при
  стабильности — как NetEQ. Цель — минимум задержки при гладкости.
- **Дроп неполного кадра:** при потере фрагментов кадр выкидывается целиком, не
  кормим декодер мусором; после потери ждём ближайший keyframe (детект по SPS).
- Аудио jitter-buffer уже адаптивный — свести к общей логике/часам.

### M2 — Канал обратной связи (RTCP-lite) — фундамент всего адаптивного
Лёгкое сообщение приёмник→отправитель по надёжному каналу:
- доля потерь, джиттер, RTT, оценка полосы приёмником;
- **PLI — запрос keyframe** (после потери/входа нового подписчика).
Без этого отправитель слеп. PLI сразу чинит «серое после потери» **и** позволяет
поднять интервал периодических keyframe (меньше тяжёлых всплесков → меньше
периодического статтера). Разблокирует M3 и M4.

### M3 — Congestion control + адаптивный битрейт (чинит переполнение канала)
Корень нашего статтера на узком/рваном канале — фиксированный битрейт переполняет
полосу. Отправитель адаптируется по фидбеку (M2):
- битрейт энкодера на лету (`MediaCodec.setParameters` PARAMETER_KEY_VIDEO_BITRATE)
  по простому loss-based AIMD (как базовый GCC);
- второй рычаг под нагрузкой — **снижение разрешения/fps** (до 480p/15fps).

### M4 — Восстановление потерь (гладкость при реальной потере)
- **FEC** (XOR-паритет) — избыточность, чинит умеренную потерю **без RTT**
  (реалтайм-дружелюбно). Приоритетно для keyframe.
- **NACK + выборочная ретрансмиссия** недавних фрагментов в пределах дедлайна
  (без RTT-штрафа когда потерь нет). WebRTC юзает оба адаптивно.

### M5 — A/V-синхронизация (lip-sync)
Сейчас приёмник назначает СИНТЕТИЧЕСКИЙ pts, реальных меток нет. Нужно:
- общие монотонные часы захвата: метить аудио и видео одним временем на
  отправителе, слать метки в потоке (**изменение формата провода**);
- на приёме — выравнивать показ по меткам, ведущие — аудио-часы (аудио критичнее),
  видео подтягивать к ним.

### M6 — Аудио-обработка (AEC/NS/AGC)
- Сначала дёшево: Android `AcousticEchoCanceler` / `NoiseSuppressor` /
  `AutomaticGainControl` (AudioEffect, часто аппаратные) на сессии AudioRecord.
- Если мало — интегрировать APM из libwebrtc (тяжелее).
Без AEC громкая связь эхает — это блокер для юзабилити звонков.

### M7 — Масштаб и полировка
- **Simulcast/SVC** для мультипати: слать несколько слоёв качества, сетка
  подписывает низкое для мелких тайлов, высокое — для активного говорящего
  (ложится на модель масштабируемости в `design/call-ui.md`).
- **Active-speaker** по энергии звука (уже в планах звонков).

## Порядок
M1 (сразу, независимо) → M2 (фундамент) → M3, M4 (параллельно, оба на M2) →
M5 (нужны метки в проводе) → M6 → M7.

## Честная оценка
Это по сути переизобретение куска WebRTC. M1–M3 закрывают 80% боли (статтер,
переполнение, восстановление keyframe). M4–M6 — для «как взрослые». Каждая фаза
самостоятельна и проверяема на нашем стенде (телефон↔эмулятор + adb logcat
resyncs/loss).
