# Транспорт против фильтрации: прокси с расшифровкой и ТСПУ

**Статус:** исследование, **после беты**. Ни кода, ни решения пока нет — записано, чтобы
не потерять разбор (2026-11-03). Когда дойдём — оформить ADR и запись в журнале движка.

## Задача

Peerage должен работать из сети, где:

- **Явный прокси обязателен** (прописан в настройках). Без него в сети не ходит ничего.
- Через прокси **`CONNECT` на голый IP запрещён** (любой) — только по домену.
- Прокси **расшифровывает TLS** (свой корневой сертификат), дальше — **чёрный список
  доменов + регулярки** по содержимому. Глубже, по словам пользователя сети, не смотрит.
- Снаружи всё это идёт через **ТСПУ**.

Конкретный случай — сеть техникума у знакомого пользователя. Сеть и её правила — их; если
человека поймают, последствия у него. Мы делаем общий механизм устойчивости к фильтрации,
а не «обход конкретного админа».

## Вывод

**Reality не нужен.** Его смысл — пройти мимо прокси, который НЕ вскрывает TLS (подделка
рукопожатия под браузер, сверка метки в `session_id`). Здесь прокси TLS вскрывает — Reality
он просто разорвёт. Зато после вскрытия проверка примитивная, и хватает **обычного HTTPS с
WebSocket к домену не из чёрного списка**: внутри — бинарный поток Yggdrasil, а в нём —
сквозное шифрование Peerage. Регулярке цепляться не за что.

Yggdrasil 0.5.13 это почти умеет сам: пиры `wss://` (а также `ws://`, `socks://`,
`quic://`; `ygg_add_peer` передаёт URI как есть).

## Что проверено в исходниках yggdrasil-go v0.5.13

- `src/core/tls.go`: `InsecureSkipVerify: true`, проверка сертификата — всегда `nil`.
  **Подменённый сертификат прокси `wss://` примет** — доверять корню техникума не нужно.
  Подлинность пира — ключами в рукопожатии Yggdrasil; мост закреплять `?key=<pubkey>`.
- `src/core/link_wss.go`, `link_ws.go`: прокси — `http.ProxyFromEnvironment`, то есть только
  переменная `HTTPS_PROXY`; системные настройки Windows не читаются (без прав админа
  `set HTTPS_PROXY=...` в `cmd` хватает).
- **Блокер:** `dial` сам резолвит домен (`findSuitableIP`) и подставляет **IP** в URL, поэтому
  прокси получает `CONNECT 1.2.3.4:443` — в этой сети запрещено. Плюс если DNS наружу не
  ходит, до прокси дело не доходит вовсе.
- Приметы, видимые прокси после расшифровки: заголовок `Sec-WebSocket-Protocol: ygg-ws`,
  первый кадр начинается с байт `meta`. Для общих регулярок (vpn/proxy/tor…) вряд ли важно;
  если сработает именно это — своя тонкая обёртка в `libygg`.

## План

0. **Опыт без кода в Peerage** (как только будет пропатченный `yggdrasil.exe`, см. п. 1):
   - Мост на VPS: свой нейтральный домен, Caddy (сам берёт Let's Encrypt — прокси, вскрыв TLS,
     сам откроет TLS до моста и, вероятно, проверит сертификат) → `/путь` на Yggdrasil с
     `Listen: ["ws://127.0.0.1:PORT"]`.
   - В сети: `yggdrasil.exe` (сборка — `scripts/build-ygg-windows.sh`), конфиг
     `IfName: none`, `Peers: ["wss://домен/путь?key=…"]`, перед запуском
     `set HTTPS_PROXY=http://прокси:порт`. Проверка — `yggdrasilctl getPeers` (Up).
1. **Правка yggdrasil-go (несколько строк):** в `ws`/`wss`-dial при заданном прокси не
   резолвить домен и не подставлять IP — отдать прокси имя (`CONNECT домен:443`). У нас —
   `replace` в `ygg/go.mod` на копию с патчем (подхватят `libygg` и Android); заодно —
   PR в upstream (честный баг для всех за доменным прокси).
2. **Peerage:** поле для своего пира (`wss://…?key=…`) и настройка прокси в «Сеть»;
   для Android — прокси передать в Go-слой (переменная окружения процесса или явный параметр).
3. **ТСПУ:** снаружи это обычный TLS до домена моста. Мост на зарубежном VPS рискует попасть
   под обрывы длинных соединений к зарубежным хостингам (по сообщениям 2025 года — после
   ~15–20 КБ; не проверено). Мост на российском VPS, скорее всего, обходит.
4. Обновить модель угроз (`threat-model.md`): что маскировка скрывает (содержимое, протокол
   для простых фильтров) и чего нет (поведение: долгий поток к одному домену, ритм звонков).

## Открытые вопросы к пользователю сети

- Просит ли прокси логин? NTLM/Kerberos (учётка Windows) Go не умеет — нужна прослойка;
  Basic — пишется в `HTTPS_PROXY` (`http://user:pass@прокси:порт`).
- Пускает ли прокси WebSocket (`Upgrade`)? Если нет — запасной транспорт поверх обычных
  HTTP-запросов (как meek / XHTTP в Xray), это уже своя работа.
- Компьютеры сети или телефон в её Wi-Fi? (Для `wss://` с выключенной проверкой
  сертификата разницы почти нет, но для Android прокси надо прокинуть отдельно.)

## Если однажды понадобится Reality (прокси без расшифровки, умный DPI)

Разбор схемы, предложенной Gemini, — чтобы не повторять:

- `CONNECT разрешённый-домен:443` ведёт на настоящий разрешённый сайт, а не на мост —
  в CONNECT должен быть адрес моста.
- SNI российского банка на зарубежном VPS выдаёт сам себя (ТСПУ сверяет SNI и IP);
  маскироваться надо под сайт, правдоподобный для этого хостинга.
- «Вычислить математически невозможно» — только против активного зондирования; поведение
  и TLS-в-TLS видны.
- ClientHello не писать самим: uTLS (BSD-3) и REALITY из Xray (MPL-2.0, совместима с
  GPL-3.0) на Go; встраивать в `libygg`, а не в Rust и не через SOCKS-петлю.
- Нужны мосты (серверы) и их раздача; маскировку надо сопровождать за релизами Chrome —
  устаревшая хуже никакой (ложное чувство защиты).
