# Дорожная карта

Спецификация (что строим) — [p2p-messenger-spec.md](p2p-messenger-spec.md).
Этот файл — **порядок и зависимости** работ. Текущее состояние и решения —
в [README.md](README.md).

## Принципы
- Полный P2P, без своего сервера для данных (единственное внешнее — push-пробуждение).
- E2E-шифрование; для медиа конфиденциальность даёт транспорт Yggdrasil.
- **Эффективность без потери качества** (минимум аллокаций/копий/оверхеда; цель — 1080p60 + чёткий звук, без экономии на битрейте).
- Общее Rust-ядро (`core`/`transport`/`messenger`/`media`) переиспользуется всеми платформами. Десктоп (Slint) — эталонная реализация; Android — порт поверх того же ядра.

## Готово
- [x] Идентичность (ed25519 → Yggdrasil/Curve25519/BIP39), персистентность.
- [x] Транспорт Yggdrasil через FFI (без TUN/root), вход в глобальную сеть.
- [x] E2E-чат: протокол, NaCl Box, сессии, presence, keepalive, повтор до Ack.
- [x] Контакты (TOFU) + история сообщений на диске.
- [x] Десктоп-UI на Slint (контакты/чат/мой код/инфо), Holo-тема.
- [x] Лёгкий медиа-транспорт (демукс чат/медиа, бинарное обрамление, без Ack/крипто на пакет).
- [x] Аудио-кодек Opus (полное качество) + джиттер-буфер; сквозная проверка на синтетике.

## Фазы

### Фаза A — 1:1 аудио-звонок  ✓ ГОТОВО (звук — ручной тест на железе)
Завершила медиа-вертикаль: голос десктоп↔десктоп.
- [x] Сигнализация `CallInvite/CallAccept/CallEnd` (проверено headless).
- [x] Движок `p2p-call` (cpal: мик→Opus→сеть; приём→джиттер→Opus→динамики; mute).

- Осталось: реальный звук протестировать на железе (мик/динамики недоступны в WSL).

### Фаза B — 1:1 видео  ✓ ГОТОВО (реальный захват — на железе)
- [x] Фрагментация кадров + реассемблер; H.264 (openh264); унифицированный Call.
- [x] Захват камеры (nokhwa, через push-источник) и экрана (xcap); рендер в UI;

### (архив) Фаза B — план
- H.264 кодек (десктоп: openh264 для простоты линковки; аппаратное — позже/на Android).
- Захват камеры (Linux v4l2 / Windows MF; крейт `nokhwa`).
- Пакетизация: фрагментация кадра в ≤MTU (frame_id + frag_idx + marker) + реассемблер; расширение медиа-обрамления для видео.
- Рендер в Slint (Image из YUV→RGB), явный выбор разрешения/fps (как в ТЗ), адаптация fps/битрейта под сеть.
- **DoD:** видео 720p→1080p между десктопами на прямом пиринге; деградация под сеть.
- Зависит от: Фаза A (автомат звонка, согласование). Риск: throughput 1080p60 через оверлей (нужен прямой/короткий путь), CPU софт-энкода.

### Фаза C — Шаринг экрана (десктоп + телефон)
- Десктоп: `ScreenSource` (xcap) — pull, уже есть (за фичей `capture`).
- Телефон (Android): захват через **MediaProjection** (Kotlin) — это **push**.
  Решено архитектурно: `PushSource`/`FrameFeeder` в `media` — внешний захват
  (MediaProjection через JNI) кладёт кадры, `Call` забирает как обычный
  `VideoSource`. Один видео-конвейер для камеры/экрана и для desktop/Android.
- UI-переключение камера/экран; на Android — запрос разрешения MediaProjection.
- **DoD:** трансляция экрана в звонке на десктопе и на телефоне.

### Фаза D — Пробуждение в фоне (ОПЦИОНАЛЬНО, решается в Фазе G)
Дата-плейн всегда чистый P2P/E2E; это только про «разбудить приложение в фоне на
телефоне» (десктоп держит mesh сам, сервер не нужен). На Android ОС усыпляет фон,
поэтому нужна одна постоянная служба. Делаем **подключаемым выбором пользователя**:
- **A. Serverless** (по умолчанию): foreground service держит сам узел Yggdrasil
  (висящее уведомление). Ноль серверов; тяжелее по батарее.
  - [x] **Реализовано (Android):** `ConnService` — foreground-сервис (type
    specialUse/dataSync) с PARTIAL_WAKE_LOCK + WifiLock(FULL_HIGH_PERF), стартует
    при открытии приложения. Закрывает баг «телефон отваливается от сети при
    погасшем экране» (MIUI/Doze замораживали процесс → пир-линк рвался по
    таймауту → звонок умирал, нужен был рестарт). Проверено на железе: сервис
    foreground, оба лока удерживаются.
- **B. Self-hosted push**: лёгкий коннект к СВОЕМУ ntfy «где-то ещё» (VPS/домашний
  ящик), через него только зашифрованные пинги. Экономит батарею. Паттерн UnifiedPush.
- Клиент `p2p-ntfy` (publish/subscribe) уже написан как опциональный бэкенд для B.
- **Реализуется на уровне Android (Фаза G)**, ядра/десктопа не касается.

### Фаза E — Группы (MLS)

- [x] Сетевой онбординг: обмен KeyPackage по сети (invite→KeyReply→add) ✓.
- [x] **E3 — групповые звонки** (full mesh): `GroupCall` — мультикаст захвата

**Десктоп-клиент функционально полный** (чат/звонки/видео/экран/группы/настройки).

### Android — доработки после теста на железе (2026-06-15)
Проверено вживую (эмулятор x86_64 ↔ arm64-телефон, реальная mesh): чат и TOFU
работают. Найдены дефекты:
- [x] **БАГ (исправлен): видеозвонок зависал/тормозил всё приложение.** Причина —
  конвертация YUV→RGB камеры в Kotlin по пикселям (65.8% CPU) + аллокация RGB на
  кадр (GC-шторм). Перенёс конвертацию в Rust (нативно, целочисленно), планы YUV
  отдаются напрямую без математики/аллокаций в Kotlin; приём — RGBA + Bitmap.
  copyPixelsFromBuffer (без пер-пиксельного цикла); fps 30→20. Замер: камера-поток
  65.8% → 5.2% CPU.
- [x] **UX-баг: нельзя вернуться в звонок (исправлено).** Входящий invite молча
  игнорировался при `call != null`. Теперь invite от ТОГО ЖЕ собеседника =
  переприглашение: гасим протухший звонок и показываем новый входящий, его можно
  принять и переподключиться. От другого пира во время звонка — игнор (заняты).
  Rust звонок не гардит (движок пересоздаётся, медиа маршрутизируется по ключу
  пира). Возможное улучшение: бесшовный авто-accept переприглашения; глэр-резолв.
- [ ] **UI-оверхол (глобально):** заменить эмодзи на нормальные иконки (vector
  drawables / material icons); единые размеры и отступы у однотипных элементов
  (кнопки топ-бара, ряды списков, поля). Сейчас вёрстка «на глаз».
- [x] **MediaCodec (аппаратный H.264) внедрён** — как в ТЗ. Отправитель:
  Camera2 → input-Surface энкодера (zero-copy) → access-unit'ы в Rust
  (`callSendVideo`, фрагментация). Приёмник: `callPullVideoPacket` → MediaCodec
  декодер → SurfaceView (zero-copy на экран). Rust больше не кодирует видео
  (openh264 убран из Android-пути). Проверено на телефоне: двусторонний
  видеозвонок, кодек на железе (MtkOmxVenc 3.9%, vpud-декодер 5.8%), 518/800%
  CPU простаивает. Заодно ушёл и фриз.
- [ ] **Экран настроек медиа (Android):** битрейт/частота/каналы/режим Opus и
  разрешение/fps/битрейт видео — всё уже есть в `core::settings`, нужен UI и
  проброс в звонок. Подтверждённый запрос пользователя: «повысил бы битрейт, но
  лучше сделать настраиваемым». Аудио на 96 кбит/с «норм, но не песня».
- [ ] Видео-полировка: аспект SurfaceView (сейчас растянут), своё превью камеры,
  переключение фронт/тыл, MediaProjection (экран). Общая полировка по мере тестов.

### Открытые по итогам тестов 15.06 (на завтра)
- [x] **Архитектура потоков**: UI больше не зовёт Native напрямую (poll/ticker/ops
  на фоне) — ANR-зависания как класс устранены. **Нужен стресс-тест пользователя**
  (несколько минут чат+звонок) для подтверждения, что больше не виснет.
- [x] **B2 — видео фризит раз в несколько кадров (ИСПРАВЛЕНО, подтверждено на железе: «гораздо плавнее»).**
  Корень: приёмник темпировал на фикс. 24 fps, а камера через AE-диапазон отдавала
  до 30 (и падала до 15 в темноте) → рассинхрон темпа/захвата → дрифт `renderClock`
  → периодический жёсткий сброс-рывок. Фикс: камера пинится на ФИКСИРОВАННЫЙ fps
  (`pickFpsRange` предпочитает `[fps,fps]`), приёмник темпирует ровно столько же
  (VIDEO_FPS=30). Present-timestamp пейсинг сохранён.
- [x] **B3 — аудио не очень чёткое (исправлено, нужен ретест).** Корень: декод шёл
  «по приходу» (приёмный поток дренировал весь джиттер на каждый пакет в 1-сек
  `out_ring`) → `jitter_depth` гейтил только первый кадр, реального сглаживания не
  было. Фикс: декод/PLC перенесён в `pull_audio` — ровным темпом потребителя
  (`AudioTrack`); джиттер реально сглаживает; добавлен потолок бэклога в
  `JitterBuffer` (анти-латентность).
- [x] **B1 — БАГ: при видеозвонке аудио зациклилось → шум (исправлено, нужен
  ретест).** Закрытые наушники исключают акустическую петлю → это была дивергенция
  Opus PLC: под видео-заторами аудио теряется пачками → `decode(None)` подряд →
  PLC уходит в тональный шум. Фикс: счётчик подряд идущих PLC, после `MAX_PLC=3`
  (~60мс) выдаём тишину вместо растущего PLC. Плюс декод развязан с видео-потоком
  (см. B3) — видео-нагрузка больше не сбивает аудио-конвейер.
- [ ] Перенести тот же потоковый принцип на десктоп (Slint-колбэки зовут ядро
  напрямую).

## Фаза H — Глобальный редизайн «Telegram + Discord» (Android-first)

Крупный разворот продукта (решено 2026-06-15). Не «переписать всё разом», а по
ФУНДАМЕНТАМ, держа приложение рабочим. Бóльшая часть желаемых фич сводится к 4
переиспользуемым подсистемам.

**Зафиксированные решения:**
- **Комнаты звонков = MLS-группы + маячок присутствия** (переиспользуем готовую
  крипту/членство MLS и десктопный mesh `GroupCall`; не плодим новый примитив).
- **UI = плавающее окно поверх других приложений** (Android PiP/bubble или
  draw-over-apps) + единый тёмный компактный «оверлейный» стиль (как оверлей Steam).
- **Офлайн-доставка = чисто serverless** (очередь на диске + фоновый флаш по
  присутствию; foreground-сервис расширяет окна пересечения). Промежуточный
  self-host релей (режим B push/ntfy) для истинной офлайн-доставки — опционально позже.
- **Сначала Android**; ядро/протоколы общие, десктоп догоняет.

### H1 — Постоянные комнаты (звонки как в Discord)
- **Маячок присутствия в звонке**: подписанный периодический сигнал «я в комнате
  R, аудио/видео вкл» членам группы. Комната жива, пока в ней ≥1 участник; хост
  не нужен; зайти можно в любой момент.
- Android: подключить mesh-`GroupCall` (готов на десктопе: мультикаст, свой
  джиттер/декодер на участника) + join-anytime.
- **Сетка участников** + клик → фуллскрин (Compose поверх per-participant
  SurfaceView/декодеров).
- 1:1 становится комнатой на двоих (текущая модель invite/accept-only уходит;
  частный случай — F1-фикс возврата в звонок).
- Сюда же сворачиваются: P1 аспект SurfaceView, P2 своё превью, P3 фронт/тыл, F2.

### H2 — Контент-адресные блобы (фундамент медиа)
- Чанками, адресация по хэшу (BLAKE3), pull-запрос «дай блоб X», возобновляемо,
  лимиты размера/типа (анти-DoS). Прямая тяга с устройства собеседника.
- Первый потребитель — **аватарки** (периодическая сверка хэша → тяга при смене).
- Готовит H5 (картинки/видео/файлы/превью) почти бесплатно.

### H3 — Присутствие + офлайн-очередь сообщений (serverless)
- Очередь исходящих на диске; фоновый флаш по событию «пир в сети». Усиление
  текущего reliable-слоя поверх готового foreground-сервиса.

### H4 — UI-оболочка
- Плавающее окно поверх (overlay/PiP) для звонка; единый тёмный «оверлейный» стиль.
- Пере-оформляем экраны по мере готовности H1–H3. Сворачивает старый UI-оверхол.

### H5 — Богатые сообщения (потом)
- Картинки/видео/файлы (на H2), markdown, превью ссылок. Полировка «как в телеге».

### H6 — Аудит безопасности + багфикс-проход
- Новая поверхность: блобы (untrusted-контент, парсеры/CVE, DoS размером),
  комнаты (авторизация входа), overlay-разрешения. Повторить скан зависимостей.

## Кросс-секущие решения (зафиксировать заранее)
- **Крейт `call`** — оркестрация звонка (сигнализация + аудио/видео-треки) поверх `messenger` + `media`. Один автомат на 1:1 и групповые звонки.
- **Согласование кодеков** — в `CallInvite/CallAccept` (offer/answer-lite по надёжному каналу), затем медиа течёт.
- **Формат фрагментации видео** — спроектировать в начале Фазы B (frame_id/frag_idx/marker), чтобы аудио и видео делили один медиа-канал.
- **Десктоп — эталон**; Android начинается, когда контракты ядра по звонкам устаканились (Фазы A/B), если приоритет не сменится.
